**当前 6 条闭环**：吃 → 档位提升 → 能吃更危险的东西 → 胃袋会满 → **吐出来（弹药）/ 压下去（等级）** → 体积下降 → 能过窄缝。

本轮**顺手修掉了一个"写了但没做"**：喷吐从来没有减过 `player.volume`（`spit.ts` 的注释、提交信息和旧文档都说它会减），
所以"极限瘦身"一直只是承诺，代码里只有受击会减体积。现在喷吐和消化共用**同一本账**——每件东西在吞下时记下自己
加了多少体积，离开时按这个数还回去——于是吃进去再吐出来严格守恒，而"清空胃袋 → 体积下降 → 过窄缝"真的成立了。

已建立的**可复用约定**（后续工作请沿用，不要另起一套）：

- 可调数值一律进 `config/mechanics.json5`，中文注释，**加载器逐项校验并点名报错**
- 只为**最基础的样式**写代码，具体观感由作者手调（见 `AGENTS.md`）
- 不给危险物发明血量；命中效果优先用**击退/位移**这类已有语义
- 判定规则只写**一处**（如 `canEatHazard`），碰撞与视觉标记问同一个函数
- 测试用 Playwright，`e2e/` 下每个机制一个 spec；**默认不跑全量**（见 `AGENTS.md`）

## 二、待办

### 06 · 消化压缩 —— 已完成

**Status:** `done` · 规格第四节第 2 条

长按左下角上方的绿色压缩钮，胃袋里最老的那件开始被压下去：**体积按进度还回去，同时产出成长能量换「可吞等级」**。
完整机制说明在 `README.md` 的"消化压缩"一节，数值在 `config/mechanics.json5` 的 `digest` 段。

**当时提出、现在已经定下来的那个问题**——"质量转化为成长能量"要有一个去处：

- **选定：提升吞噬档位。** 消化的收益是**可吞等级**（`canEatHazard(kind, volume, tierBonus)`），而不是体积或体积上限。
  理由是规格第二节自己写了"可吞等级属于质量"；而且它是唯一**立刻可见、可量化**的收益——体积 1 的气泡消化 6 条鱼之后
  真的能吃鱼了。代价是它提前实现了一部分里程碑 10（体积/质量分离），这正好给 10 提供了证据。
- 否决"提升体积上限"：当前上限 10 已经高于最后一档 8.5，收益要再吃回来才体现，偏弱。
- 否决"直接提升体积"：和"缩小"矛盾。

**落地时改掉的两处计划**（都值得记下来）：

1. **压缩是独立的按钮，不是喷吐键的长按。** 计划写的是"长按压缩"，第一版把它做成了喷吐键按住。
   写完才发现那会让"吐 vs 消化"不再是一个选择——**按下去就已经吐了一发**；更糟的是胃袋里只有一件时
   **永远无法消化它**。所以加了第四个控件（左下角上方，比喷吐钮小）。
2. **收益跟着"体积真的流出了多少"走，而不是"这件东西消化完了"。** 前者让账是平的（消化到一半再吐出去，
   已经流走的那份**早就付过钱**了），也堵住了"残血时靠消化刷等级"的路（消化最多把你压到剩 1 点血，不会杀死你）。

**验证**：`e2e/digest.spec.ts`，6 个用例 × 2 个 project 全绿。其中"账是平的"和"消化能熄灭引信"是回归风险最高的两条。

**顺带发现的既有问题**（不是本轮引入的）：`e2e/spit.spec.ts` 的击退用例在 **desktop 上一直是红的**——
它把靶子放在 `0.9 泳道宽` 处，而那个位置在关卡回收带之外，弹丸射程只有 `0.88 泳道宽`，所以**永远打不到**；
手机 project 视野更高才侥幸通过。已在 `HEAD` 的独立 worktree 上复现确认，然后把距离改成 `0.55` 修掉了。

### 07 · 危险食谱：负面食物

**Status:** `needs-info` · 规格第五节第二类

规格把可吞噬物分三类：可吞噬 / **可吞噬但有副作用** / 不可吞噬。第三类已经做了（不可吞的红色标记，目前默认关闭），
第二类完全没做。规格列了五种：

| 目标 | 副作用 |
|---|---|
| 海胆 | 从内部造成伤害 |
| 电鳗 | 让气泡短暂失控 |
| 腐败物 | 降低消化效率 |
| 炸弹鱼 | 在内部倒计时 |
| 油污 | 占据容量且难以排出 |

**这一类是整个设计里风险决策的来源。** 没有它，吞噬永远是纯收益，玩家会无脑吃；有了它，"这个东西值不值得吃"才成立。

**为什么标 `needs-info`**：这需要**五种新的实体**（海胆/电鳗/腐败物/炸弹鱼/油污），每一种都有自己的行为和外观。
在写代码前需要确认两件事：

1. 是一次做完五种，还是先做一到两种（建议先做**海胆**和**炸弹鱼**——一个内部持续伤害、一个内部倒计时，代表两类完全不同的风险）
2. 它们是否**也出现在危险物列表**（即不吞也会伤害你），还是**只有被吞下才有副作用**

**依赖**：炸弹鱼的"内部倒计时"和油污的"占据容量难以排出"都要求胃袋有**逐件状态**。
**这一层 06 已经做了**：`StomachItem` 现在有 `kind`、`age`、`mass`（它给气泡加了多少体积）和 `digest`（消化到几成），
`Stomach.tick(dt, rate)` 逐帧推进并回报 `{ burst, drained, completed }`。所以 07 要加的是**每件东西的行为**，
而不是从零搭这层。给副作用加状态，最省的做法是照 `digest` 的样子在 `StomachItem` 上再加一个每帧推进的字段
（并在 `StomachTick` 里回报它），而不是让 `Stomach` 认识危险物——它现在刻意不认识，除了一串 `kind`。

### 08 · 配方系统

**Status:** `needs-triage` · 规格第八节

连续吞下特定组合获得临时能力。规格给了 6 种配方（轻盈气体 / 坚硬核心 / 生物电流 / 爆裂混合 / 净化循环 / 捕食本能）并建议单局 6~10 种，且**用图标提示缺的最后一个材料**。

**为什么标 `needs-triage`**：这是**横切系统**，不是单个机制。它需要：

- 胃袋或一个"最近吞过的种类"的记录
- 一个配方表（配置）
- 临时能力的生效与过期（`Player` 已经有一套 `skillRemaining` 类似的计时器可以借鉴）
- **HUD 上的材料提示**（这一条工作量可能比配方本身大）

而且要小心：配方如果只是"吃了 A+B 就变强"，它会**和成长阶段抢角色**。规格自己也提醒了"为了避免玩家只看体积数值"。
建议先和作者确认：**配方是"更强的成长"还是"不同形状的成长"**（前者会和阶段重复，后者才有意义）。

### 10 · 体积与质量的分离

**Status:** `needs-triage` · 规格第二节

规格要求**质量**（吞噬了多少物质：冲撞力、抗洋流、可吞等级、技能消耗、得分倍率）与**体积**（碰撞范围：口径、吸附范围、转向、缝隙、被打中概率）**分离**，玩家通过消化把质量转成永久能力、同时缩小体积。

**这一条我目前是刻意简化的**：现在质量就是体积（`volume` 一个量），因为规格的第一节（食物链反转）先做时它足够，
而且它让机制立刻可玩、可测。**但规格作者明确说了两者不应完全同步**——所以这是一个**已知的欠账**，不是遗漏。

**为什么标 `needs-triage`**：这是**改地基**，会牵动几乎所有文件（体积出现在每一处判定里）。
在动手前需要确认：

- 分离之后，"血量"跟哪个走？规格没说。现在血量 = 体积 / `hitCost`。如果体积可以主动缩小，血量就会跟着掉，**这会让消化变成自杀**，除非血量跟质量走
- 得分倍率跟质量走的话，结算是要改的

**建议**：等到 06（消化）做完之后再评估——消化是唯一同时改变两个量的操作，它会**暴露出简化的具体代价**，
那时候再决定要不要分离，比现在空想更准。

### 11 · 场景与关卡：更多障碍用法

**Status:** `ready-for-agent`

障碍系统已经做好并接进了时间线，但只用了最基础的两种排布。规格里还提到几种用法没做：

- **渔网**：木箱的变体，撞不碎但可以撕开
- **封路木箱**：需要喷吐才能打碎的厚墙（现在木箱一炮就碎）
- **强制高速卷屏**：规格第十节把它列为最克制吞噬气泡的环境之一
- **狭窄通道群**：连续的珊瑚窄缝，把"极限瘦身"从单次事件变成一段体验

**为什么单列**：这是**内容**，不是机制。机制已经在了，加东西就行。
优先级应该低于 06/07——但**成本也低**，适合夹在大的里程碑之间做。

## 四、待确认的调参问题

这些不是待办，是**需要作者判断的数值问题**，我列出观察但没有答案。

1. **阶段晋升阈值**：`absorbToStage2 = 12`、`absorbToStage3 = 20`。一局 60 秒，到阶段 3 需要 32 只。
   按现在的泡泡密度是否偏慢？（未实测过一局能吃到几只）
2. **`volumeMax = 10`**：为了让五档食物链全部可达而设。是否偏大？
3. **过饱引信 5 秒**：够不够把东西吐出来？配合 `capacity = 3`、喷吐冷却很短，理论上按三下就解除了。
   现在还有第二个答案：按住压缩，`capacity ÷ compressPerSecond = 3.3 秒` 就能腾出空间。**这两个数要一起调**
   ——`compressPerSecond` 调小到 0.3 以下，过饱就只剩喷吐一个答案，消化在那一刻失去意义。
4. **珊瑚耐久 3.5**：`projectileDamage` 1.2 × 蟹 1.6 = 1.92，所以珊瑚要两炮。是否合适？
5. **`minGapFraction = 0.17`**：约等于体积 1 气泡直径的 1.6 倍。紧还是松？
6. **消化的汇率**（本轮新增，最需要手调）：`energyPerTier = 1.0` 意味着**四条鱼换一级可吞等级**，
   `maxTierBonus = 3` 意味着最多把体积门槛降 3 档。一局 60 秒能吃几只危险物决定了这三级是"后期奖励"还是"中期就到顶"
   ——**没有实测过一局能吃几只**（和第 1 条是同一个未知数）。想削弱消化就调 `energyPerMass` 或 `energyPerTier`。
7. **`passivePerSecond = 0.12`**（本轮新增）：不按键时一件要 8.3 秒。它现在是"白送的涓流"——
   调大到 0.3 以上，被动消化本身就能熄灭引信，`compressing` 的代价（禁吸附 + 受伤加倍）就没人愿意付了。
   设成 0 就等于"只有按住才消化"，也是一种合理的设计。

调这些不需要改代码，改 `config/mechanics.json5` 存盘即可。

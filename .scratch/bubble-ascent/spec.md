# 《气泡的伟大冒险》/ The Great Bubble Adventure — Design Spec

GameJam 主题：**涌现**。9:16 竖屏、手机优先、网页发布。

单人开发。基调：**轻松搞笑 + 操作挑战**。核心体验是**平滑上升的心流通道**被
**突然的规模爆发**打断的那种爽感。

---

## 1. 一句话

玩家操控一个从海底诞生的气泡一路上升 500 米浮出海面；沿途吸收气泡变大、躲避四种危险物、
捡技能、在三次"突然一下全来了"的爆发里活下来。**你越强，世界越凶。**

## 2. 核心循环

```
上升 -> 抢气泡变大 -> 变大招灾（鱼更多、判定框更大） -> 变危险 -> 死亡或浮出海面
```

设计上唯一的自平衡张力：**你变强的速度和世界变凶的速度在赛跑**。

## 3. 空间与进度

- 设计分辨率 **540 × 960**（9:16），等比缩放居中，桌面留黑边
- **0m = 海面，500m = 海底**，单局目标 **~175 秒**
- 速度非匀速：早期几乎不变，最后 100m 才真正加速（指数 2.4）
  - `500m:1.70  400m:1.84  300m:2.46  180m:4.05  100m:5.71  50m:7.02  0m:8.55` m/s
  - 改参数后**必须**用 `node scripts/solve-ascent.mjs` 重新解峰值（该积分无初等原函数）
- 进度表现：**深度条**（右缘）+ 顶部实时「距海面 XXXm」读数；**涌现事件挂在固定深度上**

## 4. 操作

| 输入 | 桌面 | 触屏 |
|---|---|---|
| 左右 | `A`/`D` 或方向键 | 屏幕上**任意位置拖动**（气泡向手指缓动） |
| 加速 / 刹车 | `空格` / `S` | 右下角**竖向滑杆**（上=加速、下=刹车），**粘滞**：松手后保持数值 |
| 技能 | `Shift` | 滑杆上方（D4 实装） |

- **加速时操纵性下降**（`boostSteerFactor`，由反解得出）：加速时横向推力只剩约 1/3，
  但**阻尼不变**——所以"冲的时候转不动，松手还留着惯性"，而不是一松手就变龟速。
  这是让加速键成为**取舍**而不是**免费升级**的关键。
- 气泡恒上升，**永远不会下沉**；玩家只决定"多快"

### 触屏事件的接线方式（踩过两次坑）

**触屏控件不在 Pixi 的命中检测体系里做路由。** 指针事件由 `app.stage` 上的监听器统一接收
（`stage.hitArea = { contains: () => true }`），再手工判断落在哪个分区。

两次失败的设计：

1. 每个控件各自一个可交互 `Graphics`，靠显示列表顺序和 `eventMode` 继承来分流；
2. 合并成一个整屏可交互 `Graphics`，其余图形设 `eventMode='none'`。

**两次都是同一个症状**：水面拖动正常，**右下角滑杆完全收不到事件**——而诊断显示
`containsPoint` 返回 true、`getBounds` 正确、所有 prune 标志正常、坐标空间也对
（`lastDown` 记录证明 `pointerdown` **根本没进入处理函数**）。
最后是彻底绕开命中检测才解决的。

> **教训**：当命中检测的"应该命中"和实际路由矛盾时，不要把时间花在考古上——
> **改成不依赖命中检测**，问题就整类消失了。

### 移动端尺寸（"只在左上角 1/4"的真相）

两个独立错误叠在一起：

1. `resizeTo: window` 在移动端会在**布局视口还没稳定时**锁定尺寸。改为
   `ResizeObserver` 监听容器 + 显式 `renderer.resize(w, h)`，
   并监听 `orientationchange` 与 `visualViewport.resize`。
2. 我自己的诊断字段把 `renderer.width` **又除了一次 resolution**，于是打印出
   `195x422` 这种"只有一半"的假象，让我一度去追一个不存在的 bug。

**`renderer.resize(w, h)` 接收的是 CSS/逻辑像素**，内部会自己乘 resolution 得到后备缓冲。
Pixi 里取逻辑尺寸要用 **`renderer.screen`**，不要用 `renderer.width / resolution`。

> 排查移动端尺寸问题的正确姿势：把 `window.innerWidth/Height`、`visualViewport`、
> 容器的 `getBoundingClientRect`、`canvas.clientWidth/Height`、`canvas.width/height`、
> `renderer.screen`、`resolution` **一次性全打出来**。用 `window.__GB.frame()` 即可。

### 横向手感（几何决定，不是口味）

### 世界尺度与"铺满屏幕"
游玩区域：**`WORLD_WIDTH = 361m` 宽 × `WORLD_HEIGHT = 190m` 深**，
视口把它**按宽度铺满整个画布**（`scale = 画布宽 / WORLD_WIDTH`），所以左右黑边在任何比例下都不存在。

**为什么世界是"宽大于深"的**：气泡的屏幕尺寸由 `BUBBLE_LANE_RATIO`（占**水柱宽度的比例**）
决定，而不是像素常数。早期版本把纵向密度固定成 `视口高 / 540`，结果铺满宽度后气泡在桌面上
只占水柱的 **_3.3%_**（实测，不是估算）——变成一颗小点。把气泡尺寸绑到水柱宽度上，
它就随游玩区域一起缩放。

**两个不变量**（这是横向手感在跨设备时能保持一致的原因）：

- 世界是**各向同性**的（两个轴同一个缩放），所以圆永远是圆；
- 横向操控用**横穿时间**表达、气泡 x 用**水柱比例**表达。水柱多宽就自动标定多快。

> ⚠️ `VIEW.width / VIEW.height` 是**设计盒**（540×960），**不是**可视范围。
> 把它当成可视宽度用，会算出只占 44% 屏幕的水柱——这个坑踩过一次。

### 横向手感（用比例表达，跨设备一致）

气泡 `x` 是**水柱宽度的比例**（0..1），`vx` 单位是**水柱宽/秒**。
这样水柱多宽、屏幕多大都不影响手感，只有标定出来的常数会变。

**这些常数不是推出来的，是运行时反解出来的**：`src/lateral.ts` 会**模拟真实的更新循环**
并二分求解加速度，直到**实测横穿时间**命中目标；按水柱宽度缓存，resize 时重算。
用 `node scripts/solve-lateral.mjs [水柱宽]` 可以在不启动浏览器的情况下检查同一套数学。

> ⚠️ **不要用闭式解推这些常数**。速度是**渐近逼近**稳态值的，所以 `accel / damping`
> **不等于**从静止出发实际能达到的速度。用它反解会让你以为横穿要 1.5 秒、实测却是 2.4 秒。

| 量 | 目标/实测 | 说明 |
|---|---|---|
| 巡航横穿水柱 | **1.5 秒** | 从静止出发（水柱 361m 时 `accel ≈ 1569`） |
| 加速时横穿水柱 | **4.5 秒** | 反解出 `boostSteerFactor ≈ 0.307` |
| 时间常数 | **0.18 秒** | `1 / LATERAL_DAMPING`，决定起步多快、松手多久停 |
| 巡航最高速 | **272 水柱宽/秒** | 实测值 |
| 加速最高速 | **83 水柱宽/秒** | 比巡航慢——这就是"冲的时候转不动" |

**每帧推力增量是 `accel / 120 ≈ 13.1 水柱宽/秒`**（加速时 4.0）。
`stopSpeed`（松手后的硬停止阈值）**必须远低于这个值**——首版把它设成了
平方形式的 `0.0036`，比单帧增量还小，结果**每帧都把刚加上的速度清零，气泡完全不动**。
这是"输入没反应"的真凶，只有靠 `updates`/`dt` 计数才能定位。
`solve-lateral.mjs` 现在把这个不等式作为**硬断言**，违反就退出码 1。

### 坐标空间（血的教训）

| 空间 | 单位 | 内容 |
|---|---|---|
| **世界空间** | 米 | 气泡、尾迹、海雪、深度尺 —— 由 `Camera.applyTo()` 统一变换 |
| **屏幕空间** | 像素 | 水体渐变（全屏底）、水柱遮罩与边线、HUD、结算横幅 |

**绝对不要把世界坐标当屏幕像素用**，也不要反过来。首版混用两者，一次产生三个 bug：
海雪跑到水柱外面、深度尺被加了两次 letterbox 偏移、气泡被钉在左墙上。
另外 `Graphics` 的路径在 `clear()` 之前会一直保留——**忘记 `clear()` 会画出跨越屏幕的残留连线**。

水体渐变**铺满整个画布**（不是只铺水柱），水柱靠一层压暗 + 青色边线标出边界；
这样画面读起来像海洋，而不是"一条发光的窄带"。

## 5. 核心机制

- **体积 = 血量**，但**血量是固定的命中次数**：`hitPointVolume = 0.2`，出生体积 1 → **5 下**。
  一次受击固定扣 1 点，所以**受击代价与体积无关**；变大买到的是**更多血条**。
- **大吸小**：你比对方大（≥0.92 倍）就吃掉它；比对方**小**就撞伤自己（金色描边 = 吃不动）
- **技能 = 单独掉落的道具**：**单槽**（捡新替换旧）、主动按键、**有限使用次数**
- **天赋 = 纯被动自动触发**；3 种诞生方式开局随机
- **受击后 0.8 秒无敌闪烁**（跨类型统一规则，防止被鱼群连击秒杀）
- 主得分 = **最大体积**（鼓励吃）
- 死亡：慢镜头破裂（1.5s）→ 极简结算卡 → 自动重开；浮出海面走同一段演出

### 加速只作用于玩家（不是整个世界）

**这是两种不同的上升速度，驱动两件不同的事**：

| 量 | 用途 |
|---|---|
| **玩家实际上升速度**（含 boost） | **只**驱动视差层——玩家爬得快，水里的碎屑确实应该更快掠过 |
| **巡航上升速度**（不含 boost，深度曲线本身） | 驱动所有**可收集物**的相对运动 |

泡泡的屏幕速度是 `巡航速度 − 泡泡自身上升速度`。**如果用加速后的速度，加速就会把整片海洋一起放大**，
而不只是改变玩家在水里的位置——这正是踩过的 bug：按加速时，下降的泡泡仿佛也一起被放大了。

> ⚠️ **不要用 `player.vy / speedMultiplier` 反推巡航速度**。
> 斜坡进行中这个除法只是近似，会把 boost 的一小部分泄漏进泡泡运动（实测 0.08% 漂移）。
> 直接**从深度曲线算**，它天然与 boost 无关。

由 `scripts/boost-scope.mjs` 断言：`collectableMotionUnchanged` 要求固定参考下的求解
**逐位相同**（连"加速"和"松开"两次采样都是 `0.5787217078137916`）。

### 上升速度与加速（两个可配置量）

| 配置项 | 含义 |
|---|---|
| `boostMultiplier` | **最大速度**：按住加速时上升速度的倍数（当前 **2.4**） |
| `boostAccelSeconds` | **加速度**：从巡航到上限所需的时间常数（当前 **0.8s**） |

> **`boostAccelSeconds` 用"时间"而不是"m/s²"表达**，因为上升速度本身随深度变化，
> 恒定加速度会在每个深度以不同速率到达上限。时间常数让整段爬升的手感一致。
>
> 趋近是指数的，所以 **~63% 的变化发生在这个时间内，约 3 倍时间后基本到位**。
> 设为 **0 即恢复瞬间切换**（这是加这个配置之前的行为）。

实测（`scripts/accel-ramp.mjs`）：配置 τ=0.8s → **观察值 τ=0.731s**，曲线全程吻合。

> ⚠️ **不要用 `sleep()` 跨 CDP 往返来测量时序**。每次采样一个往返，会把延迟算进去，
> 让**正确的**加速曲线看起来偏慢。要在**页面内**用 `requestAnimationFrame` +
> `performance.now()` 采样，并且 `Runtime.evaluate` 要带 `awaitPromise: true`。
> 这个坑我踩了两次才定位。

### 触屏操作：拖拽 + 加速按钮

- **拖动任意位置** → 气泡横向追向手指
- **右下角圆形加速按钮** → 按住加速，松开回落巡航

> **滑块改成按钮**，因为加速现在是"加速过程"而不是瞬间切换：
> 没有需要"留在那里"的值，按住才是自然表达。

> ⚠️ **测试时序的关键教训**：诞生演出（`intro`）期间 `step` 会提前返回，
> **什么都不动、也不结算碰撞**。任何依赖"游戏在跑"的断言都必须先等到 `playing`，
> 而且**等待超时要抛错而不是静默继续**——我原来的循环静默超时后继续跑，
> 导致"重生后"那一段其实是在暂停的游戏上测量，产生间歇性失败。

### 关卡定义：长度是输入，时长是输出

**`DEPTH_TOTAL` 是关卡长度（每关不同），不是从时长反推出来的。**

> ⚠️ **这个项目曾经反着做**，后果很具体：为了凑 175 秒，曲线指数被逼到 2.4，
> 于是**前 40% 的爬升速度几乎不变**——看起来就是静止的水。
> **时长不该是输入。** 一旦它是输入，其他参数就都变成"被解出来的"，
> 而"解出来的形状"不保证好看。

`src/levels.ts` 里每关只声明：

| 字段 | 含义 |
|---|---|
| `totalDepth` | **关卡长度**（米） |
| `metresPerScreen` | **一屏装多少水**（米） |
| `ascentSpeedBase` / `Peak` / `CurveExponent` | 上升曲线 |
| `landmarks` | 该关的路标（含标签，属于关卡内容） |

**这两个值必须同进同退**，它们的比值才是"观感"：

```
screenHeights = totalDepth / metresPerScreen     ← 爬升有几个屏高
secondsPerScreen = 时长 / screenHeights          ← 一个屏高花多久（最直白的"看起来快不快"）
```

当前关卡：`500 / 190 = 2.63` 屏高，**44.8 秒/屏**，总时长 **117.91s**（输出）。

> **新增关卡怎么定？** 想保持观感就把 `totalDepth / metresPerScreen` 保持不变，
> 时长自然随长度等比变化；想保持时长就把 `ascentSpeedBase/Peak` 跟着 `totalDepth` 等比缩放。
> 两者都改就会同时改变观感和时长。
>
> `metresPerScreen` **不是自由参数**：它决定一屏上有多少收集物、它们看起来多大。
> 调小 → 水更少、东西更大、反应空间更小；调大 → 反之。
> 当前值是按"一屏约 20 个收集物"选的密度。

`assertLevelSane()` 在启动时校验并**抛错**（长度/速度为正、峰不低于基、屏高数在 1.5~12 之间），
避免发出去一个玩不了的关卡。

**没有"目标时长"这个配置项了。** `nominalAscentSeconds()` 积分真实曲线得出时长，
`solve-ascent.mjs` 只**报告**它（不再反解），并用闭式解交叉验证数值积分。

### 体积经济（试错三次才定下来）

**唯一自洽的模型**：血量 = 固定命中次数，体积 = 承载这些命中的池子。

| 体积 | 可承受击数 | 抵消一次受击 |
|---|---|---|
| 1.0（出生） | **5** | 0.73 个泡泡 |
| 2.0 | 10 | 0.73 个泡泡 |
| 3.2（上限） | 16 | 0.73 个泡泡 |

> ⚠️ **踩过的两个坑，方向相反，但错误相同**——都让"一次受击的代价"依赖于体积大小：
>
> 1. **伤害 ∝ 当前体积**：乘性衰减，大泡泡能扛 13 下、小泡泡 8 下。**变大反而更容易**，与设计相反。
> 2. **伤害 = 固定绝对值**：可承受击数确实恒定，但大泡泡受伤要 3 倍泡泡才补回来——
>    因为**奖励固定、代价缩放**。
>
> 正解是让**受击固定 = 1 个命中点**（按基础体积扣除）。可承受击数随体积增长是"变大"的**收益**，
> 而**变大的代价由更大的判定框承担**——这正是第三轮就定好的设计。
>
> **教训**：不要为了让某个数字"看起来恒定"去扭曲机制。先问"这个量该不该恒定"。
> "可承受击数不该恒定"——它就该随体积增长，否则没人有动力去吃泡泡。
> 由 `node scripts/solve-volume.mjs` 断言。

### 水体的运动（为什么"东西看起来没动"）

核心恒等式：

```
水中任何物体的屏幕速度 = 相机速度 + 它自身相对水体的速度
而相机速度 == 玩家的上升速度
```

**泡泡流的下降速度与玩家上升速度成正比**（`bubbleFallMin/Max = 10~40` 倍）。
把流绑到上升速度上，**整条水柱会随上升加速**——这才是"我在水里往上冲"的样子。
收益：**加速键立刻有视觉反馈**（上升 ×1.55 → 整条流同帧 ×1.55）。

实测（390px 手机）：起点泡泡流 **76 px/s**，到海面约 **370 px/s**。

> ⚠️ **试过并否决的两种方案，都有实测数据**：
>
> 1. **按深度缩放**（`ascentSpeedAtDepth × random`）：靠近海底时相对屏幕速度只有 **~0.2 px/s**，
>    看起来就是静止的水。这是"东西没在动"的真凶。
> 2. **固定水柱比例带**（0.055~0.13 水柱宽/秒）：确实在动了，但**与上升完全无关**——
>    爬得再快，水流速度不变。
>
> **一个硬约束值得记住**：175 秒一局意味着**整屏平均只能滚 3.6 px/s**
> （整段爬升 = 2.9 个屏高，与比例尺无关）。所以远景背景**永远**不可能看起来在动，
> 只能靠有相对速度的层次来表现速度。近景雪粒保留为 3~9 倍（**慢于**泡泡流，
> 让泡泡读作"正在交互的快速物体"，雪粒只是背景质感）。

**生成分布必须分两种**：

- **开局填充** → 铺满可视范围，否则开局是一片空洞
- **后续替补** → 从可视范围**上方**生成，成为从顶部流入的水流

> 不要在 `spawnBubble` 里对 y 做 `Math.min(DEPTH_TOTAL, ...)` 钳制——那会把初始填充
> 全挤在同一个 y 上，形成屏幕顶部一条"泡泡带"。
>
> **泡泡带稳定 `id`**，让探针能追踪**同一颗**泡泡。测"最近的那颗"两次采样根本不是同一个
> 对象，会得出无意义的数字（这个坑踩过）。

> **探针的采样间隔要和被测速度匹配**：泡泡在起点不到 1 秒就穿过整屏，
> 用 500ms 间隔采样会得到 `null`。`motion.mjs` 默认 150ms。

### 泡泡的运动（真实物理：大泡泡上升快）

**真实世界的规律**：气泡越大上升越快。因为浮力随体积增长，而阻力随横截面积增长，
所以终端速度随半径递增。在游戏关心的尺寸范围内近似**线性于半径**。

因此游戏里的推导是：

```
泡泡相对玩家的屏幕速度 = 玩家上升速度 − 泡泡自身上升速度
```

| 泡泡大小（相对玩家半径） | 自身上升 | 屏幕上的表现 |
|---|---|---|
| 0.15× | 0.15 × 玩家 | **快速向下**（玩家超过它） |
| 1.0× | 1.0 × 玩家 | **几乎静止**（并排同行） |
| 1.6× 以上 | 1.6 × 玩家 | **向上移动**（它比玩家快） |

> **收益：不靠任何 UI，尺寸就变得可读**——向下飘的是能吃的，往上跑的是吃不动的。
>
> 实测相关性 **-1.0**（在 26 个泡泡上），由 `scripts/rise-speed.mjs` 断言。

**注意量级**：一切都相对玩家上升速度缩放，所以起点差距只有 1–2 px/s（微妙），
到海面是 3–5 px/s（13 秒穿越窗口内很明显）。**这是物理自洽的结果，不是缺陷。**

**小泡泡抖、大泡泡稳**：摆幅按大小缩放（表面张力相对水流扰动）。
纯装饰，且刻意保持很小——**绝不能大到改变泡泡何时经过玩家**。

### 生成分布：踩了三次的边界条件

生成位置用**可见高度的比例**表达（`SPAWN_ABOVE_FRACTION = 0.15`），
而不是绝对米数。绝对米数在可见高度变化时含义完全不同：

> ⚠️ 我在这条边界上**连续错了三次**：先是"上方一整个屏高"（生成即被回收），
> 再是固定 55m、再是固定 60m 对 20m 的回收边界。
> 固定 60m 在 454m 的视野里只占 13%，**新泡泡刚好在屏幕外一点点，
> 以 1.5 px/s 靠近要 30 多秒才进画面**——场上 26 个泡泡，屏幕上永远只有 1 个。
>
> **硬约束**：`CULL_ABOVE_FRACTION` 必须**严格大于** `SPAWN_ABOVE_FRACTION`，
> 否则泡泡在创建的同一帧就被销毁再重建，形成空转。两个值现在写在一起。

**开局填充 vs 后续替补**（用"本轮已生成数量"区分，不能用在世数量——
玩家每吃掉一个就会掉下来）：

- **开局填充** → 从视野底部一直铺到**会被回收的最高位置**，让玩家一开始就在有内容的世界里
- **后续替补** → 只在视野上方一点点，成为从顶部流入的水流

**下方回收余量要大方**（`CULL_BELOW_FRACTION = 0.35`）：大泡泡上升比玩家快，
会跑到视野**下方**却仍属于泡泡场。在那里回收等于**持续删除最大的泡泡**，而它们最重要。

### 键盘手感（固定速度，无加速度）

键盘横穿水柱 `KEYBOARD_CROSSING_SECONDS = 2`（**线性旋钮**：数字减半，速度翻倍）。

> ⚠️ **不要用"缩放加速度"来调键盘**。试过 `keyboardSteerScale = 0.7` 再到 0.05，
> 结果 0.05 时上限仍然是 **8 水柱宽/秒（约 3900 px/s）**——因为被缩放的加速度基数本身极大，
> 5% 仍然是荒谬值。二元轴 + 加速度模型**无论怎么缩放都调不出来**，只能改成固定速度。

> ⚠️ **不要用固定像素阈值做断言**。`KEYBOARD_CROSSING_SECONDS` 是给玩家调的旋钮，
> 任何写死的期望值都会在玩家调参后立刻失败。断言要**从运行时值推导**。

**唯一自洽的模型**：血量 = 固定命中次数，体积 = 承载这些命中的池子。
跑 `node scripts/solve-volume.mjs` 看曲线，它带硬断言。

| 体积 | 可承受击数 | 抵消一次受击 |
|---|---|---|
| 1.0（出生） | **5** | 0.73 个泡泡 |
| 2.0 | 10 | 0.73 个泡泡 |
| 3.2（上限） | 16 | 0.73 个泡泡 |

> ⚠️ **踩过的两个坑，方向相反，但错误相同**——都让"一次受击的代价"依赖于体积大小：
>
> 1. **伤害 ∝ 当前体积**：乘性衰减，大泡泡能扛 13 下、小泡泡 8 下。**变大反而更容易**，与设计相反。
> 2. **伤害 = 固定绝对值**：可承受击数确实恒定，但大泡泡受伤要 3 倍泡泡才补回来——
>    因为**奖励固定、代价缩放**。
>
> 正解是让**受击固定 = 1 个命中点**（按基础体积扣除）。这样可承受击数随体积增长（这是"变大"的**收益**），
> 而**变大的代价由更大的判定框承担**——这正是第三轮就定好的设计，不需要靠削减血量收益来实现。
>
> **教训**：不要为了让某个数字"看起来恒定"去扭曲机制。先问"这个量该不该恒定"。
> "可承受击数不该恒定"——它就该随体积增长，否则没人有动力去吃泡泡。

## 6. 涌现引擎

**三条规则：**

1. **鱼吃气泡会分裂**（过阈值 → 两条）—— 唯一能让数量指数增长、产生雪崩的规则
2. **鱼感知半径随玩家体积增长** —— 让「变大招灾」有可量化的载体
3. **水母/垃圾优先附着最大的气泡** —— 强者被优先针对

**一条设计原则：天赋有反噬。**

> 你的保命手段就是敌人的繁殖手段。

**三段事件（脚本骨架，强度由系统算）：**

| 深度 | 事件 | 作用 |
|---|---|---|
| 180m | 鱼群（15～25 条） | 第一次真正的"手忙脚乱"，教会玩家这游戏会这样 |
| 320m | 气泡潮 | 表面是奖励，**实际是把玩家变大，为 420m 埋雷** |
| 420m | 终局爆发 | **强度按玩家当前体积动态缩放**；最后 80m 是窄缝 |

> 讲给评委的话：「**不是我安排的第 2 分钟刷鱼，是你变大了，所以世界变凶了。**」

**性能护栏（必须做）：** 指数增长会压垮手机。设**硬上限**，超限后转为**群体行为**
（合并渲染、集体转向），而不是继续生成新实体。

## 7. 内容清单

### 3 个诞生方式（天赋，纯被动）

| 天赋 | 被动效果 | 反噬 |
|---|---|---|
| **鱼屁泡** | 被鱼接触时自动放屁，冲开周围的鱼 | 屁变成气泡 → **喂鱼 → 鱼分裂** |
| **汽水泡** | 上升更快、横向惯量更大（更快更难控） | 碳酸尾迹也是气泡 → 也在喂鱼 |
| **深海淤泥泡** | 初始体积 ×1.3、受击缩小更少 | 体积大 → 更容易被鱼锁定 |

### 6 个技能（单槽，主动，带次数）

每个都对应一种危险物或一个具体痛点，**没有换皮的**：

1. **冲刺**（3）—— 短时间大幅加速上升：逃包围 / 抢进度
2. **诱饵泡**（2）—— 扔出假气泡吸走附近所有鱼：**唯一能"清场"的技能**
3. **漩涡**（1）—— 把周围气泡吸向你：快速变大
4. **臭云**（2）—— 一小片区域推开垃圾/水母：治"被拖拽"与"减速"
5. **硬壳**（2，3 秒）—— 无敌并撞开一切：危机保命键
6. **爆散**（1）—— 以你为中心向外爆开：终局爆发的救命键

### 4 种危险物（各有不同的"动词"）

| 危险物 | 动词 | 数值 | 喜剧反应 |
|---|---|---|---|
| **小鱼** | 追猎、成群 | 接触 -20% | 被诱饵泡骗走、互相挤成一团 |
| **水母** | 减速 | -40% × 1.5s，扭动可缩短至 0.5s | 被你顶一下会萎缩一下 |
| **垃圾袋** | 吸住拖拽 | -5%/秒，猛拽或技能可挣脱 | **挣脱时它自己破了** |
| **螃蟹/海星** | 上弹 | 1.2s 预兆（沙尘+弧线可见） | **被弹飞后四脚朝天挣扎** |

> 喜剧的做法是**"已有元素的意外反应"**，不是"多做一个角色"。

**实现要点（`src/hazards.ts`）**：

- **危险物必须从视野上方进入**，且**不能**用 `Math.min(DEPTH_TOTAL, ...)` 钳制。
  起点时视野顶部离关卡天花板很近，钳制会让危险物**凭空出现在屏幕中央**——
  和当年把收集物挤成一条带的那个坑是同一个。
- **螃蟹必须"两段式"激活**：危险物从生成到接近玩家要 20 多秒，
  如果引信从生成就开始烧（1.2s），**预兆弧线永远来不及被看到**。
  改成玩家进入 `crabArmDistanceMeters` 才布防，再走 1.2s 引信。
  > 这条很关键：螃蟹是唯一**可能有利**的危险物（把你弹上去），
  > 预兆是它"公平"的全部依据。看不见预兆 = 随机惩罚。
- **诱饵是偶发插曲，不是默认结果**（`fishBaitChance = 0.25`）。
  试过 0.5：小鱼追猎**通常**以走神告终，鱼群就不再是威胁，**玩笑吃掉了机制**。
- **垃圾袋的"抓住"必须是单调计数器**（`HazardField.grabs`），不能采样布尔值：
  抓取可能在**同一帧**被挣脱，事后读 `gripping` 什么也证明不了。
- **被减速的显示画在玩家身上**（紫色外环），不是状态栏——
  减速是关于"气泡在哪"的惩罚，玩家的视线不该离开自己在操控的东西。

实测四种动词（`node scripts/hazard-verbs.mjs`）：

| 危险物 | 命中 | 减速 | 弹射 | 抓取 | 净增高 |
|---|---|---|---|---|---|
| 小鱼 | 1 | 0 | 0 | 0 | 0.3m |
| 水母 | 0 | 1.31s | 0 | 0 | 0.2m |
| 垃圾袋 | 1 | 0 | 0 | **1** | 0.4m |
| 螃蟹 | 0 | 0 | **23.8 m/s** | 0 | **+5.9m** |

## 8. 死亡与终点

- **死亡**：1～1.5s 慢镜头破裂（炸成一群小气泡飘上去）→ 极简结算卡
  （深度 / 最大体积 / 用时 / 最高纪录）→ **点击即重开**
- 硬约束：**死亡到能操作下一局 ≤ 3 秒**；**没有暂停菜单**
- **终点**：冲破水面 + 慢镜头水花 + 停顿 + **「啵」地破裂** + 短白屏 → 结算卡写
  「你变成了海面上的一朵浪花」。屏幕水渍特效为**可砍项**

## 9. 表现

- **美术：程序化几何 + 渐变/发光，零美术素材。** 颜色承担玩法信息
  （紫色=水母、褐色=垃圾），无需额外 UI 教学
- **镜头**：气泡固定在屏幕**下方 75%** 处（`PLAYER_SCREEN_Y_RATIO`），世界向下滚。
  上方 3/4 屏是"即将进入的水域"，威胁能提前看到。
  > **相机偏置的符号容易写反**：相机应放在气泡**上方** `(ratio - 0.5) × 视口高`，这样气泡才在中心
  > **下方**。首版写成了相减，偏置被镜像，气泡跑到了 38%（偏上）。
  > 这类 bug 靠看图容易误判，用 `probe-layout.mjs` 读 `bubbleScreen.yRatio` 断言。
- **气泡绘制只用 `circle` / `ellipse`**。首版用 `Graphics.arc()` 画高光弧，它在 Pixi 里留下了
  一条从气泡指向水柱边缘的残留直线；换成普通圆之后消失。这是第二次被 `Graphics` 的路径残留咬到
  （第一次是忘记 `clear()`）。
- **引导**：开场直接播天赋诞生动画（约 1.6s），无文字教程
- **音频**：CC0 音效包（Kenney 水下/气泡）+ **只做环境音，不做 BGM**；
  越深越静、越接近海面越明亮 —— 环境音本身就是免费的进度反馈

## 10. 技术

- TypeScript **7.0.2** + Vite **8.3.1**（Rolldown）+ PixiJS **8.21.0**
  - Vite 8 用 Rolldown 转译 TS，**不依赖 TypeScript 编译器**，所以能跑与 TS 版本无关
  - `build.minify` 必须是 `true`/`'oxc'`，**不能用 `'esbuild'`**：esbuild 只是可选 peer
    dependency，pnpm 默认不装，会直接导致构建失败
  - 已实测：TS 7.0.2 的类型检查与 PixiJS 8.21 的 `.d.ts` 完全兼容
- 场景**完全程序生成**，没有手工摆的场景
- 全部手感参数集中在 `src/config.ts` 的 `tuning`，**运行时可改**：
  控制台 `window.__GB.tuning` 直接改数值，立刻看到效果
- 验证：`pnpm typecheck`、`node scripts/smoke.mjs`（headless Chrome + CDP，
  检查帧推进、数值正确性、终点重置路径、控制台异常）

## 12. 已知风险

1. **🔴 无人驾驶 vs. 可玩**：目前玩家唯一的主动输入是左右 + 加速。躲避本身可能不够有趣，
   真正的乐趣必须来自「加速上升」与「横向机动」的张力。
   **必须在 D1 验证，不能等到 D7 才发现游戏不好玩。**
2. **🟠 涌现指数爆炸 → 手机卡死**：分裂规则是指数的，必须做种群自我调节。
3. **🟠 反噬可能读不出来**：玩家不会知道"是我的屁在喂鱼"。必须给「鱼吃气泡」加
   **可见的即时反馈**（小爆点 + 鱼变大 + 分裂动画），否则最好的设计会变成玩家的困惑。
4. **🟠 纵轴速度与横轴操控的耦合**：终段又快又乱时，横向操控还跟得上吗？
   可能让人手忙脚乱（好），也可能让人失控（坏）。**这条线很细，要实测。**
5. **🟠 体积经济**：吃多少气泡涨多少、鱼吃几个气泡分裂 —— 这两个数必须**一起调**，
   它们是同一个经济的两端。

## 13. 已废弃的方案（不要再回头）

- **Godot 4**：这台机器上没装过，且它网页导出默认多线程（依赖 `SharedArrayBuffer`），
  不发 COOP/COEP 头就打不开。而这个游戏的场景是程序生成的，**根本没场景可摆**
- **吸收按体积解锁技能**：曾考虑过，改成"技能=独立掉落道具"以换取更高的重玩性
- **纯时间倒计时进度条**：爆发期进度会纹丝不动，产生的是绝望而不是涌现感
- **一击必死**：涌现爆发期会变成不合理的暴死
- **纯脚本刷怪**：主题上讲不响——评委问"哪里体现了涌现"时答案会是"第 2 分钟刷一波鱼"
- **BGM**：会挤占调玩法的时间，且信息量高于环境音、争夺注意力
- **第 5 种中立生物（海龟）**：喜剧改做进已有元素里，比多做一套美术/行为便宜得多

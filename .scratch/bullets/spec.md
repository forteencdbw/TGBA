# 玩家的子弹：会加速、会胀大

## 1. 这句话

**子弹射出去之后一直在加速、也一直在变大**——所以"飞得久"和"长得大"是同一件事，而"飞得久"由速度曲线决定。

这给了两条**互相排斥**的路：把速度堆满（子弹又小又快，没长大就出屏幕或打中了），或者把加速度压低（子弹又慢又大，一路胀成一个大圆）。

---

## 2. 现状

| | |
|---|---|
| 速度 | `speedPerSecond: 1.6`，发射时定死，**全程匀速** |
| 半径 | `radiusRatio: 0.011`，**恒定**；绘制和命中判定共用这一个值 |
| 射程 | `lifeSeconds: 2.2`（存活秒数），超时消失 |
| 三张卡 | `弹速 +25%` / `大弹丸 +30%` / `射程 +40%`，都乘在各自的常数上 |
| 伤害 | `damage: 1`，与体积、速度都无关 |
| 外观 | `image: "玩家子弹"`（一张像素画贴图）+ `imageScale: 2` |

---

## 3. 决策

### 3.1 两条曲线，都是连续的

**速度**：从初速**匀加速**到最高速，到顶之后保持。三个"阶段"（初始 / 加速 / 最高速）是这条曲线的描述，不是三个跳变的档位。

**体积**：随子弹的**年龄**线性增长。只跟时间有关——不跟速度直接挂钩，速度是通过"影响它还能活多久"间接影响大小的。

两条都是**连续**的，因为子弹在屏幕上的时间只有一两秒：离散档位在这么短的时间里看起来是"啪"地变大一次，而真正的气泡是慢慢胀的。

### 3.2 体积没有上限

唯一的限制是 `lifeSeconds`（它能活多久）。加一道人为的天花板会让"堆射程"在后期变成一张被截断的卡。

**代价是知道的**：一颗长射程的子弹会变成屏幕上一个越来越大的圆。它不挡路（子弹不阻挡玩家），但会挡视线。**这是数值问题不是机制问题**——真糊住视野就把成长速率调小，不加机制。

### 3.3 默认伤害与体积、速度无关

`damage` 还是那个固定值。你提的"越大伤害越高""越快伤害越高"是**两张新卡**，这一轮不做（见第 6 节）。

理由：默认就挂钩的话，"慢速大气泡流"会自动变成更强的流派，BD 就没有选择、只有正确答案。

### 3.4 命中判定用**实时**半径

画多大就碰多大——这是项目的铁律（一个比碰撞更大的绘制会让玩家以为自己安全）。子弹会因此"越飞越容易打中"，那是这个机制的自然结果，不是 bug。

### 3.5 三张卡的作用点

| 卡 | 作用 |
|---|---|
| `弹速 +25%` | **整条速度曲线一起抬高**（初速、加速度、上限都 ×1.25） |
| `大弹丸 +30%` | **整条体积曲线一起抬高**（起始半径、成长速率都 ×1.3） |
| `射程 +40%` | 存活时间 ×1.4。**它现在顺带让子弹长得更大**，这是接受了的耦合——"停留时间决定体积"这条规则一旦成立，"活得久"和"长得大"就是同一件事，拆开反而要引入一套两套记账的例外 |

### 3.6 子弹贴图保留，糊是预期内的

`image: "玩家子弹"` **保留**。连续放大确实会把像素拉成方块，但那是**接受的效果**：一颗正在胀大的气泡在像素画里"越来越糊"本身就是"它变大了"的一种表达。

（这一条推翻了我一开始的建议。我当时按"一个固定像素密度"那条规则推出应该改回矢量圆，但那条规则管的是**素材之间**的密度一致——不要让两张图一个是 32px 一个是 64px——而不是"一个东西不许被放大"。放大是这次改动的**目的**，糊是它的副作用，而它读起来仍然是一只气泡。）

## 4. 数值（默认值，你调）

```json5
"bullets": {
  // 速度曲线：初速 →（每秒加速度）→ 最高速封顶。单位都是"泳道宽/秒"。
  //
  // 这三个数一起决定**射程**（曲线下方的面积）。默认值让总射程与旧的
  // 匀速 1.6 × 2.2 秒 ≈ 3.5 泳道宽**大致相等**，所以这一版不会顺带加强或削弱枪。
  "speedStartPerSecond": 0.6,
  "accelerationPerSecond": 1.0,
  "speedMaxPerSecond": 2.0,

  // 体积曲线：发射时的半径（泳道比例），以及每秒长多少。
  //
  // 默认 2.2 秒后长到 0.0264（起始的 2.4 倍）。
  "radiusRatio": 0.011,
  "radiusGrowthPerSecond": 0.007,
}
```

按这组默认值，子弹在**1.4 秒**时达到最高速（`lifeSeconds` 是 2.2 秒），所以默认射程下三个速度阶段**都看得见**。

删掉 `speedPerSecond`（被三个曲线参数取代）。`image` 与 `imageScale` 不动。

## 5. 实现落点

| 文件 | 改动 |
|---|---|
| `src/bullets.ts` | 每帧按 age 算速度与半径；命中判定和绘制都读实时半径；**导出 `radiusOf`** 给贴图那条路 |
| `src/main.ts` | 贴图精灵池**逐颗**问 `radiusOf`，尺寸在循环内算（见 5.1） |
| `src/mechanisms.ts` | 新配置键的类型与校验；删 `speedPerSecond` |
| `config/mechanics.json5` | 上面的数值（贴图相关的键不动） |

**性能**：每颗子弹每帧两个乘法，没有新的分配。

### 5.1 绘制有**两条路**，两条都得问同一个函数

这是实际踩到的坑，值得写下来：子弹的绘制有两条路——

- `paintBullets`（`src/bullets.ts`）：代码画的圆点，**贴图还没加载好**的时候用；
- `syncBulletSprites`（`src/main.ts`）：`bullets.image` 指定的贴图精灵池，**正常运行**时用。

精灵池那条路原本在循环**外面**算了一次尺寸，用的是 `bullets.radiusRatio`——也就是**发射时**的半径，然后所有精灵共用这一个 scale。于是"3.4 画多大就碰多大"这条铁律在**有贴图的时候**变成了空话：子弹在碰撞判定里真的长大了，而画面上纹丝不动。它看起来还"对过一下"——贴图加载完成前的那一瞬间走的是圆点那条路，圆点是会长大的。

**结论**：`radiusOf` 导出，两条路都调它。一个游戏里只有一个尺寸，不是两个。顺带修好的是"大弹丸 +30%"这张卡——它也乘在同一个半径上，之前同样对贴图无效。

补一个 `scripts/probe-bullet-curve.mjs`：把半径/速度曲线按秒打印出来。`0.007` 这个数人眼看不出来是大是小，得看数字。

---

## 6. 不做的事

- **不加新卡**（加速度、成长速率）。新地基上的第一件事应该是让**基础曲线**跑通、在浏览器里试出"高速流"和"大气泡流"的手感差别——然后才知道该给卡片多少数值。
- **不加视觉护栏**（见 3.2）。
- **默认不改伤害公式**（见 3.3）。

## 7. 两张「伤害跟着子弹状态走」的卡（已实现）

3.3 拦下的是**默认**挂钩，不是挂钩本身。这一节是**付钱买耦合**：两张进全池的卡。

| 卡 | 读什么 | 公式 |
|---|---|---|
| 越大伤害越高 | **这颗子弹自己的膨胀** | `(当前半径 ÷ 发射半径 − 1) × sizeDamagePerPick` |
| 越快伤害越高 | **弹速卡的堆叠** | `(bulletSpeedMultiplier − 1) × speedDamagePerPick` |

两个 bonus **乘算**。

### 7.1 为什么一个读飞行、一个读堆叠

这是我问的第一个问题，也是这两张卡是不是"两条路"的全部。

**都读飞行时间的话它们会退化成同一张卡**：半径和速度都随 age 单调上涨，于是"堆射程"的构筑会把两张同时吃满——选择塌缩成"两张都拿"。读的东西不同，**射程流**和**弹速流**才是两个构筑。

### 7.2 「大弹丸」不喂大小卡

比值里半径倍率**会约掉**：它同时抬高 `radiusRatio` 和 `radiusGrowthPerSecond × age`。所以「越大伤害越高」奖励的是**飞得久**，实际上是一张**射程卡**（也正是它和弹速卡分岔的地方）。

### 7.3 代价：线性意味着强度与成长速率绑死

`(比值 − 1)` 是线性的，所以这张卡有多强**完全取决于 `bullets.radiusGrowthPerSecond`**。速率 0.007 时，2.2 秒寿命下比值 2.4 → 一张卡约 +28%（同「子弹伤害 +15%」一档）；速率要是回到 0.187，比值 38 → 同一张卡 +740%。这是选线性时就知道的，不是意外。

### 7.4 「弹速」从弹幕专属放开到全池

这是"全池 + 速度卡读弹速堆叠"两个决定撞出来的必然结果：专属化意味着另外两条路抽到的是一张写在牌面上的 +0%。放开的代价是弹幕路线少一张专属卡（只剩大弹丸/射程），火力身份靠那两张 + 枪管撑。

### 7.5 负数是合法配置，卡不能变成惩罚

数值范围校验已经不做了（见上一个 commit），所以 `sizeDamagePerPick: -1` 和 `radiusGrowthPerSecond: -0.2` 都是合法文件。速率和被测的量**两侧都要在 0 处夹住**——只夹一侧的话 `1 + (−1) × 1.4` 是负数，那是给鱼**回血**。这个 bug 是被 `probe-bullet-damage.mjs` 抓出来的，不是靠读代码看出来的。

### 7.6 验证

- `scripts/probe-bullet-damage.mjs`：用真实 `BulletField.update` 跑，给子弹**预设 age** 命中，验公式本身——包括"没拿卡时伤害必须和以前一模一样"、大弹丸不喂大小卡、两张乘算、负重率不惩罚。
- `scripts/probe-mutation-pool.mjs`：按三条路各抽 4000 次，验"全池"这个决定真的成立；另外验 `applyMutationPassives` 的**字符串键**没拼错（`count('sizeDamage')` 拼错会 typecheck 通过然后永远读成 0）。

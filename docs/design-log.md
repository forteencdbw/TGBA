### 第二关 BOSS：墨汁、召唤木箱、环形子弹

寄居沉船章鱼（`boss-octopus`）**去掉了默认的挥螯喷颗粒**：它的档案里不再有 `attackSpray*` 六个数（类型与校验改为可选），改为在 `hazards.bossSkills` 里登记一套技能。每次攻击（沿用自己的 `attack` 动画/`attackSprayFrame`，`attackEverySeconds` 为 **2.3 秒**，加动画约每 **3 秒**一招）**随机抽一招**：

- **墨汁**：朝玩家施法瞬间的位置抛出墨团，飞行 0.5 秒后落地成雾。雾是一个 0 血、0 伤害的 hazard `ink`，半径 0.3 泳道，持续 4.5 秒并随水流向下漂；玩家在雾内时水平、垂直和触屏拖动全部减速到 40%，离开 0.2 秒后恢复。为此补上了玩家减速的一个缺口：水平键盘与触屏拖动此前不乘 `slowMultiplier`。落地后的墨云使用贴图 `墨汁.png`（`hazardArt.ink`）；飞行中的小墨团仍由代码绘制，两者的分界是 `hazards.ink.throwSeconds`。
- **召唤木箱**：随机留一列安全口，另外两列从屏幕顶部同时生成 `fallcrate`，走和关卡内完全相同的 2 秒预警与下落；木箱之间、木箱与 BOSS 之间都没有伤害判定。**预警条现在画在屏幕最上层（HUD 与 BOSS 血条之上）**：BOSS 血条正好占据顶部，世界层的预警会被它盖住，而关卡里没有这条血条——这正是两边看起来不一样的原因。
- **环形子弹**：从 BOSS 中心向 360° 发射 12 发，弹速 0.3 泳道/秒、单发 20 伤害、每轮整体旋转 15°。弹速/伤害/外形在 `enemyBullets.shooters['boss-octopus']`（`perSecond: 0`，不参与自动瞄准射击）。

### 修复：路径串挤成一堆 / 路径上的敌人不再冲锋 / 去掉随深度变强的环境音

**① 一串里的守卫改成"沿着曲线排开"，而不是"先后出发"。** 之前靠时间线的 `staggerMeters` 让它们先后进场——同一帧进场的成员（传送过去、卷动很快时）会**完全叠在一起**，而且每个成员的曲线是**锚在自己出生点**上的，所以六条鱼其实是同一个形状画了六遍：实测横向铺开 **0 泳道**、纵向 **0 米**，就是一坨。（那个 `staggerMeters` 当时也并没有生效——见上面"路径点"一节。）

现在两处一起改：曲线锚在**摄像机**上（同一条屏上形状，大家穿过同一个地方），并且每个成员按**序号**在曲线上占据 `pathOffset = i / n` 的位置而不是靠出生时刻错开。实测同屏 8 条：横向铺开 **1.38 泳道宽**、纵向 **454 米** ✓ —— 一条一条，不再重叠。

**② 路径上的敌人只开枪，不冲锋。** 冲锋是一条**瞄准玩家的固定曲线**，而路径是**关卡作者指定的固定曲线**；两者同时生效，意味着玩家一靠近，编排好的形状就当场被放弃——本该横扫过屏幕的一串鱼改成掉头俯冲。枪保留（一边游一边打仍然是关卡要的形状 + 压力），冲锋关掉（`const charger = h.path ? undefined : ...`）。实测同屏 8 条路径鱼：`charging: 0` ✓

**③ 环境噪声床改成固定音量**（`audio.ambientVolume`，默认 0.35）。它以前**跟着深度变强**——越往上越响越亮，听起来像游戏自己在加大音量，而不是像海。你要的是"保留质感、不要上升"，这也确实是它该有的形状：**水下的声音是关卡的属性，不是气泡爬了多高的属性**，所以它由配置设一次，而不是每帧重新送一遍新数值。实测：起点与爬升到最后，`ambient 0.217 / noise 0.315` 完全不变 ✓，改配置即改音量 ✓。被否掉的 `setDepth` 留在 `src/audio.ts` 里不调用。 那是一层随深度上升的合成噪声床，问题正如它听起来那样：**越深越响**，而降下来的办法只有主音量（会把音效一起压小）。现在气氛交给每关自己的音乐（上一条新增的），一件事做完就够了。`audio.setDepth` 与音床本身留在 `src/audio.ts` 里不再调用——一次失败实验删掉比争论便宜，真觉得太静，一行就能接回来。

### 修复：过期结算卡 + 结算界面按钮"没反应" + 出场改成从下方飞入

**① 上一关的结算卡留在屏幕上**：结算卡（`finishBanner`）以前只在 `burst` 阶段淡出，所以只要新一关是从别的阶段开始的，它就**一直挂在画面上**（截图里那个"破裂 · 深度 1404m / 得分 125"就是很早以前那次死亡留下的，和当时 HUD 上的 2955 分完全对不上）。现在只有"真正结束这一局的 burst"才配得上这张卡，其它任何阶段都直接清空（透明度 + 文字），`startRun` 也一并清掉——**一个过期的分数浮在活着的关卡上，比没有卡更糟**。

**② 结算界面的【返回主菜单】"没反应"**：按钮其实**生效了**——菜单已经在面板**后面**显示出来了，只是面板没关，所以屏幕上看起来一模一样。现在 `exitToMenu` 会先把结算面板收掉：**只有一个按钮的面板，按下它就必须离开**。

**③ 出场改成"从屏幕底部飞上来"**：以前每关开头是气泡**从小到大膨胀**出来（意思是"一个新气泡诞生了"）。但这一局现在是**上一关飞出屏幕顶部**结束的，所以对应的入场就是同一个动作的逆放：气泡**从屏幕下边缘下方升起**，缓动减速、停在正常位置（`INTRO_START_SCREEN_Y = -0.18` → `0.5`，1.6 秒，期间不可操作）。膨胀的那段缩放去掉了——气泡本来就是这个大小。

实测：`screenY` 从 **-0.18** 升到 **0.5** ✓；死亡后重开，卡片被清空 ✓；结算界面按下按钮 → 阶段 `menu`、面板 `isOpen: false` ✓

### 一只生物 = 一块（新生物照这个写）

**一只生物自己的数值写在 `hazards.<kind>` 这一块里**，不散在按数字类型分的几张表之间。螃蟹是第一只搬过去的：

```json5
"crab": {
  "armDistanceMeters": 55,   // 预警距离
  "fuseSeconds": 1.2,        // 引信长度
  "launchMps": 30,           // 起爆炸开的初速度
  "apexSeconds": 1.1,        // 抛物线到顶的时间（原来写死在 src/hazards.ts 里）
  "launchScreenBonus": 2.4   // 屏幕位移的额外倍率
}
```

代码通过 `mech.hazards.crab.*` 读它；`src/hazards.ts` 里的 `hazardTuning.crabLaunchMps` 这类名字**留着**，但已经变成指向这一块的 getter，所以调用点一行没动，而"螃蟹是什么"只有一个地方可看。

**为什么值得**：加一只生物本来要同时改好几张表（血量 / 质量 / 可吞档位 / 爆破处理 / 体型 / 冲锋 / 感官数值），
漏一行只在启动时报错；一块一个之后，"这只生物是什么"是一个能读、能比较、能整个记住的东西。

**代码那半边也一样**：`src/hazards.ts` 里每只生物的**运动**是一个命名函数（`stepFish` / `stepJelly` / …），
由一张 `CREATURES: Record<HazardKind, CreatureStep>` 表分发——所以"再加一种生物"= 配置加一块 + 这里加一个函数，
而**漏了函数是编译错误**（表是全覆盖的 Record）。**共用的状态仍然共用**：进场、蓄势冲锋、走 spline、被击退、
命中闪白、泳道夹紧都在 `advanceKind` 里，因为它们对每一种生物都是"替换"或"包住"它的运动，而不是某一种的私事。

> 搬这 18 个 case 的时候没有一行是手抄的：脚本从原 case 里逐行取出、把 `break` 换成 `return`、把 `base` 换成
> `ctx.descentSpeed`，然后**对照旧代码验证**——同一条随机种子下，18 种生物 × 2 个起始位置，跑 5 秒和 25 秒，

腐败物 `digestScale`、油污 `spitChance`）——炸弹鱼本来就是一块。搬的时候只动键的位置和读取点：搬完实测数值全部一样。

### 螃蟹 BOSS 的挥螯：8 帧动画 + 喷矿物颗粒（第一关设计稿里那两件事）

第一关 BOSS 的配置（`config/levels/01-black-smokers.json5`）写的是"**横向挥螯、喷矿物颗粒**、堵住喷口制造一次猛烈爆发"。前两件现在实现了，
所以**第一关的 BOSS 第一次有了攻击**（它以前只会悬在那儿、横着游弋、撞到才扣血）。

**它做什么**：每 `attackEverySeconds`（默认 4.6 秒）挥一次螯 → 8 帧动画（抬钳 → 高举 → 下砸 → 合上 → 收势 → 回位，
每秒 11 帧、一轮 0.73 秒）→ **钳子合上的那一帧（第 6 帧）**从钳子甩出一片 7 颗矿物颗粒，朝**你当时站的位置**飞过去。

**公平性靠三件事**（和敌人的枪同一条规矩，见 `enemyBullets` 那一段）：

| 规则 | 在这里是什么 |
|---|---|
| 瞄的是**开火那一刻**的你，之后不修正 | 7 颗的目标点在**第 6 帧**用你那一刻的位置算出来，摊开 `attackSpraySpread`（默认半个泳道） |
| 飞得比你的横移**慢**，所以躲得开 | `charges.chargers.mineral.travelSeconds`（默认 0.62 秒）就是这段飞行时间 = **你的反应窗口** |
| **前摇看得见** | 前 5 帧（0.45 秒）举着钳子——这就是预警，而且**它本身就是倒计时**，所以颗粒自己不再画第二条预警弧（`telegraphSeconds: 0`） |

**颗粒不用另写一套东西**：它们是普通的 `mineral` 危险物，出生在钳子上、被给一条 `h.charge` 曲线（鱼/水母/灯笼鱼
走的是同一条二次贝塞尔），所以它们照旧会碰撞、会扣血、体积够大还能吃，飞完落点之后照旧往上漂走。

**实测**（无头驱动真实的 `HazardField`，固定玩家位置，20 秒）：

```
挥螯 4 次（4.6 秒冷却 + 0.73 秒动作 = 5.33 秒一次 ✓）
每次都在**第 6 帧**甩出颗粒 ✓   7 颗摊在 x=[90..310]（泳道 400，正好半个泳道）✓
一颗颗粒：配置 0.62 秒，实测在 0.617 秒**精确抵达目标点**（误差 0.0m）✓
```

**在哪调**：`hazards.bosses.<kind>.attackEverySeconds`（多久挥一次）、`attackSprayFrame`（第几帧甩出去）、
`attackSprayCount` / `attackSpraySpread`（几颗、摊多宽）、`attackSpraySeconds`… 等等，
`attackSpraySeconds` 与 `charges.chargers.mineral.travelSeconds` 是同一个东西的两处写法（前者是 BOSS 的意图、
后者是曲线的时间参数），**改哪个都行但要让它们一致**——当前两处都是 0.62。
动画手感在 `animations.boss-attack.framesPerSecond`（改它不用改任何别的数：甩颗粒的时刻是**帧号**，不是秒）。
（`<kind>` 现在是六只 BOSS 各自的 kind，见下面"六只 BOSS"一节；旧的 `hazards.boss` 是墓碑。）

**图像**：`src/assets/螃蟹-BOSS-攻击-1..8.png`，8 帧、512×590、`once: true`（播完停在第 8 帧，也就是回到待机姿势）。
生成用的参考图就是**待机帧自己**（`generated-images/boss-attack/reference.png`），所以是同一只螃蟹；
8 帧的构图靠"同尺寸画布 + 底部对齐 + 左右居中"钉住（钳子挥动时身体不跟着漂），细节见
`generated-images/boss-attack/frames.spec.json`。（**`generated-images/boss-attack/` 已随中间产物删除**。）

### 六只 BOSS：一个 kind 一只，而拆分的第一步是"证明没变"

六关的 BOSS 从"一个 `boss` kind + 一个共享档案 + 每关自己写一个颜色"变成了**六个 hazard kind**
（`boss-crab` / `boss-octopus` / `boss-jelly` / `boss-shark` / `boss-netshark` / `boss-eye`），
每只一份完整档案放在 `config/mechanics.json5` 的 `hazards.bosses.<kind>`（23 个字段，不再是共享的）。

**为什么非拆不可**：从前决定"它怎么动、怎么贴、怎么开火"的每一个数都是六只共用的，所以一个关卡能说的
关于**自己那只** BOSS 的话只有"多少血、叫什么、什么颜色"。结果是六场 BOSS 战里有五场是同一场画了六遍——
而且那个"什么颜色"（`boss.colour`）其实**从来没生效过**：它写进 `hazard.kind` 的 `tint` 字段，而 `tint` 只在
**代码画的那条路径**（`drawBoss`）里被读；BOSS 有贴图，走的是贴图分支，`drawBoss` 根本不会被调用。所以六个
颜色是死代码，六只 BOSS 渲染得逐像素相同。拆开之后这只 BOSS 的手感终于有地方可写。

**拆分本身先证明了"行为没变"，这一步是量出来的**：六份档案是从 `hazards.boss` **生成**的（写脚本抄，不手打
23 个数 × 6 遍），脚本断言六份与旧档案逐字段相等；`hazardArt.<六个kind>` 也各抄了一份旧的、全指向
`boss-idle` / `boss-attack` / `boss-dead`。然后用 CDP 把**旧 BOSS 与六只新 BOSS 各画一张**（位置、
`phase`、`deterministic` 全部钉死），再拿 `git stash` 切回拆分前的提交重画一张：

```
拆分前 boss      fe67243a2a408051
拆分后 boss      fe67243a2a408051
拆分后 boss-crab / -octopus / -jelly / -shark / -netshark / -eye    同上，6 张完全一致
```

**8 张图 1 个哈希**：既证明旧的没被改坏，也证明六个新 kind 画的正是旧的那一张。

**拆分顺带暴露了配置里的四条"按 kind 键的表"**，它们都是启动检查里\"每种危险物一行\"那条约定管着的：
`hazards.health`、`consumption.mass`、`consumption.edibleAtTier`、`angry.burst.hazardMode`。
六个 kind 一加，游戏**直接拒绝启动并逐个点名**（`missing from edibleAtTier: boss-crab, …`）——
这正是"数据没有编译器，那个检查就是编译器"那条经验最好的一次示范：四条表一条都没漏掉，
而且四条都不是我找到的，是启动检查找的。

**`SPAWN_KINDS`（关卡能不能用 `spawns` 摆一只出来）原来写的是 `kind !== 'boss'`**，现在改问
`isBossKind(kind)`——不然六个新 kind 里除了 `boss` 之外全都会变成可以像鱼一样摆进关卡的东西。

### 六只 BOSS 的图：一个生物三套动画

六只现在各有自己的 16 帧（`move` 4 + `attack` 8 + `dead` 4），全部走 `.claude/skills/game-asset/SKILL.md`
那条管线：真实照片 → Seedream 出 3 张候选 → 人工挑一张 → 逐帧生成 → 本地像素化 → 进游戏。

| BOSS | 关卡 | 是什么 | 参考照片 |

**三套动画共用一个画布、一个缩放、一个锚点。** 16 帧一次性归一化（见 `normalise_frames`），而不是每套各自
归一——挥螯/张伞的那几帧内容更宽，各自归一会把中位数抬高，整只生物在攻击时变大几个百分点。帧 1 是**被选中的
那张候选本身**，不是重画的，所以三套动画起止都是同一张被批准的图，生物不会在自己的动画之间漂移。

**`attack` 的节拍是写死在帧号上的**：第 6 帧是发力那一下（`hazards.bosses.<kind>.attackSprayFrame` 指的就是
第 6 帧），第 2–5 帧蓄力、7–8 收回。动手做的时候量出来的三个问题值得记在这里，因为它们是这类生成的通病：

- **`move` 的"沸腾"是量出来的**：帧间 mean |dRGB| 从 8.0（章鱼，最干净）到 27.6（水母），而"看着像重画"的那几只
  也确实在这个区间。`boil_report` 本来是为"本该静止的循环"标定的，套在 `attack`/`dead` 上报警是**用错了地方**——
  挥螯和崩塌本来就该帧间大改。
- **烟囱蟹王的第一版每帧带着 ~12% 的深青色投影**（均值 RGB 7,81,89），因为它的 `composition` 里写了"整片均匀的
  青色背景"，同时又要 `background: transparent`——两条指令互相打架，模型就留了一片地面影子。后面五只写的是
  "主体之外**完全透明**，没有影子、没有地面、没有倒影"，一张都没出现这个问题。**那一段照原样留在批记录里**，
  它是产出那 16 帧的那次运行的记录。

**旧的一只还在**（`'boss'` kind、`hazards.boss`、`hazardArt.boss` 和螃蟹那 16 帧），`src/hazards.ts` 里标成
墓碑。删它是**迁移的最后一步**，而且它现在牵连着一件必须一起做的事：`'boss'` 一删，`Object.keys(KIND_TUNING)`
就是六个新 kind，`e2e/codex.spec.ts` 的覆盖检查立刻要求**六张 BOSS 卡片**（现在只有一张 `enemy:boss`，
那处豁免就是为它写的）。所以删墓碑 = 六张卡 + 一次真正的删除，不是一次删除。

### 图集：所有贴图打进 Pixi 图集（`pnpm atlas`）

**27 张图不再是 27 个文件。**它们现在被打进 **1 页**图集纹理，配一个 TexturePacker Hash JSON；`src/assets.ts`
仍然按**你写的名字**给出一张 `Texture`（`assetTextureNow('灯笼鱼-移动')` 没变），变的是下面那层：一个名字是**某一页里的一个矩形**。

| 页 | 尺寸 | 下载 | 帧数 | 解码（GPU 持有） |
|---|---|---|---|---|
| `atlas-1` | 784×1132 | 219 KB | 27（全部） | 3.39 MB |

**实测**：请求 **21 → 3**（1 页 + 2 张远景 JPEG）；下载 **6294 → 488 KB（−92%）**；GPU 纹理 **27 → 1**；
解码 **38.94 → 3.39 MB（−91%）**——页里 84.7% 的面积是图（剩下的是给过滤留的 2px 透明缝）。

**这些数字来自三个明确的决定**，都不是打包器自己做的：
1. BOSS 那一组（16 帧）**从 1024 降到 512 宽**：显存从 77 MB 到 ~17 MB（premultiplied alpha + BOX）。
2. BOSS 那一组**像素化到 192 宽**：~17 MB → 2.4 MB。
3. **其余 11 张图也像素化**（按各自"画出来多大"定网格，见下面"像素化"一节）：图集 770 KB / 10.68 MB → **219 KB / 3.39 MB**。
   1024 的原始图在导入它的那次提交里；512 那版在 `generated-images/boss-512-before-pixelation/`、
   像素化前那版在 `generated-images/before-pixel-pass/`（**已入库**，见下面"原图"一节）。

**换图的工作流没变，多一步**：还是把新 PNG 覆盖到 `src/assets/` 同名文件上，然后跑一次

```bash
pnpm atlas          # 重新打包（Pillow + 无损 WebP），逐像素验证每一帧
pnpm atlas:check    # 只检查：图集是不是比 src/assets 里的图旧了
```

**必须记住的代价：图集是"生成物入库"，所以它会过期。**忘了重打，游戏会继续显示**旧图**，而且不会报任何错。
`atlas:check` 就是答案（它拿 manifest 里记的**字节数 + sha256** 跟磁盘上的源图比，逐张点名），但它**故意不挂在
`vite build` 上**：部署那条命令是干净的 Node 跑 `vite build`，一个能被"美术文件过期"卡住的部署，就是一天不更新的站点。

**为什么打包器是 Python、而且不在构建里**：Pillow 才有"无损 WebP + 逐像素验证"，而部署机只装 Node。所以打包**在本地**
跑、产物**入库**。解释器是**找出来的**不是假设的（`node scripts/pack-atlas.mjs` → `$DSH_PYTHON` → DSH 托管运行时 →
PATH 上能 `import PIL` 的那个），因为这台机器上 `python` 是 Windows Store 的占位程序。

**页的形状是搜出来的，不是猜的。**候选形状里的"按内容推出来的"那几个是必须的：`1024 + 2*2 + 1024 = 2052 > 2048`，
所以 **2048 宽的页一行只放得下 1 张 BOSS 帧，2056 宽放得下 2 张**——实测差 **67 MB vs 34 MB**。判分是
**解码字节 + 每页 2 MB 罚分**：只看解码字节的话，"一图一页"是理论最小值（19 页、38.9 MB、"100% 填满"），
而那正好是这次要删掉的东西。

**为什么没顺手做裁剪（trim）**：BOSS 帧是 1024² 的方图、螃蟹只占一半高度，裁掉空白大约能把图集**砍掉一半**。
但裁过的帧在 Pixi 里 `texture.width` 是**裁完的宽度**，而这个游戏每一处画笔都用 `size / texture.width` 缩放——
裁剪会把一个**打包决定**搬进**绘制代码**。要做得先让画笔改读 `texture.orig.width`，不跟加载方式一起改。
（打包器为此写死 `trimmed: false`：实测 `texture.width` 与 `texture.orig.width` 都等于图片自己的宽度。）

**"无损 WebP"不是逐字节无损，这一条是量出来的**：libwebp 的无损模式**会改写完全透明像素的 RGB**（它看不见，
所以拿来省字节）。实测螃蟹待机帧：**19.6% 的像素不同，全部是源 alpha = 0 的像素，alpha > 0 的像素一个都没变**
（可见像素最大通道差 **0**）。打包器接受这一条并**在产物里写明**；一旦有**任何可见像素**不同，它就退回 PNG
（资产管线的 `webp-verify` 是同一个规则）。
**两张远景 JPEG 不进图集**：它们是整屏背景、没有任何 sprite 从它们取图、`parallax.ts` 要的是 `<img>` 的普通失败路径，
而且 JPEG 解不了就没有无损打包可言。它们仍然走 `assetUrl()`——**这也是 `assetUrl` 现在唯一还回答的东西**。

**规则一句话：顶层 `src/assets/*.png` = 要打包的贴图；其它任何位置的图 = 它自己的文件。** 所以**背景图请放在子目录里**
（例如 `src/assets/levels/`），PNG 也一样能当背景——`assets.ts` 里那条 glob 是"排除掉顶层 PNG 和图集目录"，不是"只收 jpg"，
正是为了不让一张手工存成 PNG 的背景**悄悄消失**（顶层的 PNG 一定会被当成贴图打进图集）。

**验证**（两条都是可重复的命令，不是"看着像"）：

```bash
node scripts/probe-atlas.mjs   # 用 PixiJS 自己的 Spritesheet 解析图集 manifest + 让 assets.ts 经 Vite 解析每个名字
node .scratch/check-art-names.cjs   # 配置里的每个贴图名都能在（图集 ∪ 独立文件）里找到
```

实测：1 页全部解析成功、**27/27** 张图的 `texture.width/height` 都等于图片自己的尺寸（**没有一张被当成裁剪帧**，否则每个用它的生物都会被悄悄改大小）、**27/27** 个配置贴图名解析到**真实存在的页文件**、
`assets.ts` 没有发出任何警告；`pnpm atlas` 自己还会把每一页从**写出去的文件**里解回来、逐像素跟源图比对。

### 像素化：整套美术现在是真·像素画（一个密度，不是一个大数字）

**全部 27 张图**都过了一遍资产管线的 `pixelate()`：BOX 缩到目标网格、**每只生物一套 40 色共享调色板**、
alpha 单独重采样再贴回。原来是模型渲染（看着像素味，放大 4 倍就能看到没有像素格，是平滑渐变）。

**关键不是"用哪个网格"，而是"画到屏幕上多大"**——决定像素化看不看得见的是**一个精灵被画成多少个屏幕像素宽**：

```
现在这个密度 = 图片像素宽 / 游戏把它画出来的宽度
```

BOSS 是 **192 像素画到 ~254px**（1.3 屏幕像素/像素块），所以它读起来是像素画。
水母以前是 **118 像素画到 74px**——**像素块比一个屏幕像素还小**，所以它的像素化一直等于看不见。
灯笼鱼按 192 打的话是 3.9 像素/屏幕像素，只会更"糊"。**所以固定一个网格是错的旋钮。**

**改成一个密度**：`一个像素块 ≈ 1.4 屏幕像素`（= BOSS 被挑中时的密度），每张图的网格从**它被画出来的宽度**反推，
而那个宽度全部来自配置、不是我估的（手机泳道 412px = `computeViewport` 里的 `min(screenWidth, 900)`）：

| 图 | 画出来 | 之前（像素/屏幕像素） | 现在网格 | 依据 |
|---|---|---|---|---|
| 灯笼鱼-移动 / 冲锋 | 111px | 3.9 | **80** | `radius 0.09 × scale 1.5` |
| 盲虾 / 盲虾-蓄力 | 76px | 6.4 / 5.8 | **56** | `radius 0.066 × scale 1.4` |
| 水母-待机 1-4 | 74px | 0.6 | **52 宽**（从 1024 原图重做） | `radius 0.062 × scale 1.45` |
| 玩家气泡 | 52px | 5.5 | **36** | 气泡半径 × `imageScale 1.5` |
| 玩家子弹 | 18px | 8.7 | **12** | `radiusRatio 0.011 × imageScale 2` |
| 冲锋拖尾 | 66px/格 | 7.1 | **284**（6 格 ×47） | `sizeRatio 0.16`，**按格算** |
| 螃蟹 BOSS | 254px | 0.7 | **192**（上一轮定的，作基准） | `radius 0.11 × scale 2.8` |

**同一只生物的几张图必须同一个网格**：第一版脚本按"每张图各自的内容比例"反推，结果灯笼鱼-移动 96、灯笼鱼-冲锋 92，
盲虾 56、蓄力 64——虾一伸展开像素大小就会跳。密度只取决于 `画出来宽度 / 网格`，跟内容占多少画布无关，
所以正确的算法里**没有内容比例这一项**。

| | 像素化前 | 现在 |
|---|---|---|
| 27 张图的文件总量 | 6294 KB | **511 KB** |
| 图集 | 2 页 / 3113 KB / 25.62 MB 解码 | **1 页 / 219 KB / 3.39 MB 解码** |
| 加上 2 张远景 JPEG 的下载总量 | 6.45 MB | **0.49 MB** |

**画出来的大小没有变**（这是必须验的）：画笔用 `size / texture.width` 缩放，`size` 来自配置，所以画布永远画同样大；
会动的是"内容占画布的比例"。逐张实测（换算成屏幕像素）：**最大变化 1.29 屏幕像素**，
而最小的那张（子弹）一个像素块本身就是 1.5px——也就是说全是取整，没有一张图变大变小。

**水母是从 1024 原图重做的，不是把 118 宽的那版缩小**：把已经是像素画的图再缩一半，会让相邻像素块混在一起、
出来是糊的，那正好抵消像素化的意义。重做流程 = 原图 → `pixelate(84)` → 取四帧内容的并集裁切（52×77），
和原来那版的结构完全一致（内容贴满四边）。

**采样已经改成 `nearest` 了**（`src/assets.ts` 的 `loadPage`，一行）。上一轮我**故意没改**，理由当时写在这里：
采样是**按纹理**设的，那时 27 张图里的小怪是从 512 宽**画到 20–100px**（缩小 5–25 倍），nearest 会丢像素、动起来发抖。

### 剩下的占位：八个资产 + 五个"藏在代码里的玩法电报"

四个射手换图之后，**还剩下八个在关卡里出场、但仍然由代码画的东西**：`矿物颗粒` / `失控鱼雷` / `螃蟹` /

| 种类 | 藏在代码里的东西 | 弄丢的后果 |
|---|---|---|
| `crab` | 抛物线预警弧 + 扬起的沙 | 看不到自己会被扔到哪 |
| `bombfish` | 引信环（关闭中的倒计时） | 看不出还剩多久爆 |

炸弹鱼 **2.9**（一个均匀的深红圆球，每帧几乎一样）、电击水母 **16.3**（触手轻摆）、螃蟹 **23.7**。
螃蟹看着最糟，但**它的问题不是"沸腾"，是大小**——模型在两张里把螃蟹画宽了 9%，而 `import-sheet.py`
把每帧都缩到同一个网格宽度，于是整只螃蟹以 4fps 一胀一缩。像素化前先按**内容宽度中位数**归一之后，
它降到 **8.2**。这条归一化现在是管线的一部分（`normalise_frames`），理由是 `asset_pipeline.py` 早就写下的那条：
渲染之间的尺寸差是渲染不一致，不是"要表现的一胀一缩"。

**`--grid` 有个坑值得单独记一笔。** `sheet --grid N` 是按**整张源图**（四周留白一起算）像素化到 N 宽的，
而 uniform 布局又把文件宽度定成"内容 + 2×margin"。模型出的图四周一定有留白——海星的内容只占画布的 84.6%——
所以直接按 `画出来宽度 / 1.4` 设网格，出来的文件会**偏窄**、密度冲到 **1.66** 而不是 1.4。
**正确做法是先把原图裁到内容框**，让内容 = 画布，`网格 = round(画出来宽度 / 1.4) − 2 × margin` 才成立。
上表四个密度就是这么来的，和已入库那六张（1.36–1.44）对得上。

**海星不能用 `spin`，用的是 `volleyAligned`。** `hazardArt.*.spin` 是"每秒转多少弧度"的**速率**，而海星的五条腕
**就是**它下一轮齐射的五个方向——`stepStarfish` 沿 `h.volleySpin + i × 72°` 发射，那是一个**状态**：每轮跳一整格
（36°），而且初值是随机角。速率追不上状态，差一格就是**图在骗人**，那比没有图更糟。
`volleyAligned` 让角度直接读 `h.volleySpin`，并且**不镜像**：镜像是同一个 bug 的另一半——镜像后的海星仍然是海星，
但每条腕都跑到了错的一侧，而五重对称让这个错误**不会以"翻过来了"的样子暴露自己**。
`volleyBaseRadians` 是图里第一条腕的朝向（从原图剪影量出来是 20°），只负责把图自己的朝向对到齐射的 0 度。

**缺口已补：刺魨反击冷却时会瘪下去。** 代码画的那版在 `counterRest > 0` 时把刺缩成短桩、身体变暗，
那是"现在打它免费"的**唯一**提示；贴图版原本只有一张图，冷热一个样。现在 `hazardArt.puffer.charge` 指着
`刺魨-瘪`，`POSE_RULES.puffer` 在 `counterRest > 0` 时切到它。

**它和别的第二张图不一样，值是量出来的。** 代码版的比例是身体 ×0.72、刺 ×0.35，也就是瘪下去的轮廓
`(2×0.72 + 2×0.35) = 2.14r` 对充气的 `(2×0.95 + 2×0.75) = 3.4r` —— **0.63**。而 `import-picture.py` 会把每张图
裁到自己的内容框再缩到网格宽度，所以一张"瘪下去的刺魨"出来会和充气版**一样宽**：刺变短、身子反而更大，
**正好说反**。解法是 `asset_flow.py` 的 `pixelate_aligned`——不裁自己，按 0.63 放在**充气版的内容框**上，
并用**同一套调色板**（同一个生物，一套颜色）。参考图也不是新找的照片，而是 `generated-images/gunners/刺魨.png`，
即那只充气刺魨像素化前的渲染：这样"同一只东西换个状态"是**由构造保证**的。

### 金枪鱼：新敌人 `tuna`（`金枪鱼-游动-1..4`，4 帧游动，**只动尾巴**）

**它是"比鱼大一档的一条鱼"**：行为和鱼**完全共用**，只有体型不同。所以它的贴图只有一张（游动循环），没有冲锋姿势——
鱼也没有图，蓄势的弧线是代码画的。

**这 4 帧不是生成的，是"搬"出来的**，因为"只有尾巴动、身体别动"这件事**提示词做不到**。
第一版是逐帧生成（同一张参考图、四个摆尾相位），实测：**帧与帧之间身体有 30–73% 的像素不一样**
（每帧约 300 种颜色、四帧并集 908 种 —— 每一帧都有自己的抖动图案），整条鱼都会爬。
原因很直接：**每一帧都是一次重新渲染**，模型没有"保持这一部分不变"的能力。

所以改成：拿**你自己的那张参考图**，在**尾柄**（身体和尾鳍之间最细的那道腰）切开，只把**尾鳍**绕那一点转。
身体**一个像素都不碰**。做法：

1. **找尾柄**：不是"右边最细的一列"（尾鳍的尖端更细），而是**从身体往外走、轮廓停止变细的那个转折点**——
   实测 `x=772`（1024 宽），那里 115 个不透明像素，而身体最粗的一列是 478 个。
2. **切口放在腰后面 14px**：这样尾鳍的根部转到**身体自己的尾锥后面**去，铰链藏在轮廓里，不会在切线处裂开一条缝。
3. **四个相位 = 一条正弦取 4 个点，偏移 20°**（`+5.1° / +14.1° / −5.1° / −14.1°`）。
   **不能**取 `0/90/180/270`（那是 `0, +A, 0, −A`，会有两帧是同一张图，图集校验会（正确地）判为重复帧）。
   幅度 `AMPLITUDE_DEGREES = 15`：尾鳍尖上下摆约 7 个像素块（≈10px），嫌小就调大这一个数再跑一遍。
4. **身体是"替换"不是"叠加"**：`alpha_composite` 会让身体边缘的半透明像素和下面的尾鳍混色，
   于是身体的字节仍然会逐帧变化。所以身体覆盖到的地方**直接写字节**。
5. **四帧裁到同一个窗口**（四帧内容框的并集 + 边距）再交给像素化。
   这一步不是洁癖：管线是按**内容宽度**缩放的，如果带着各自的内容框进去，**尾巴摆出去的那一帧会被缩得更小**，
   身体就会逐帧变大变小 —— 同一个毛病换条路回来。

| 尾巴（第 47 列之后） | 帧间 **83–90%** 的像素在变（这就是动画） |

而手写像素化的那批（BOSS / 水母 / 灯笼鱼 / 盲虾…）是**每只共享 40 色**。
如果要统一，就在第 2 步之后、导入之前加一遍 40 色共享调色板量化（**必须四帧共用一张调色板**，
否则身体又会逐帧变色）；不做也不影响，只是风格上比别的东西"滑"一点。

**新生物要落到的每一处**（`Record<HazardKind, …>` 那几张表是**全量**的，所以漏一处就是**编译错误**——
这是这套结构最值钱的地方：编译器就是清单）：

| 位置 | 值/做法 |
|---|---|
| `hazards.radius.tuna` + `KIND_TUNING.tuna.radius` | **0.045**（鱼 0.035，+29%） |
| `hazardArt.tuna` | `{ front: 'left', move: 'tuna-swim', scale: 2.5, alpha: 1 }` |
| `animations.tuna-swim` | 4 帧、**8 帧/秒**、循环 |
| `hazards.health.tuna` | 15（鱼 10） |
| `hazards.mass.tuna` | 0.4（鱼 0.28） |
| `consumption.edibleAtTier.tuna` | 3（鱼 2——它更大，要更大的气泡才吞得下） |
| `angry.burst.hazardMode.tuna` | `destroy`（和鱼一样是软体小敌人） |
| `charges.chargers.tuna` | **照抄鱼那一行**（300m / 0.75s / 0.55s / 0.3 / 2.2s） |
| 代码：`CREATURES` / `CONTACT` / `CREATURE_DRAWING` | 全部指向鱼的那三个（`stepFish` / `contactFish` / `drawFish`）——**没给图时的兜底**也是鱼的身子，只是按金枪鱼的半径画 |
| `codex.ts` 的 `HAZARD_NAMES` | `'金枪鱼'`（**图鉴卡片本身还没写**：`ENEMY_PROSE` 是手写的散文，不是全量表，所以它现在不会出现在书里） |

**它现在出现在哪一关？还没有**：关卡是手写的（`config/levels/*.json5` 的 spawn 块），我故意没动你的关卡编排。
在任意 spawn 块里加一行 `{ "kind": "tuna", … }` 就行；想先在游戏里看它，控制台 `__GB.game.debugSpawnHazardOnPlayer('tuna')`
（那个钩子会**生成在玩家身上**，所以看的时候先往旁边走两步）。

**⚠️ 一个比例你可能想调**：`scale 2.5` 意味着**看得见的鱼比会撞到你的那个圈大 2.5 倍**
（画出来 97px，碰撞直径只有 37px）。这是 `scale` 的定义（只影响观感），但 2.5 是全场最高的比例——
灯笼鱼 1.35、水母 1.45、盲虾 1.4。想让它"看着多大就撞多大"就把 `scale` 调到 1.0–1.4，
**同时按新宽度重定网格**（`sheet --grid 画出来宽度 ÷ 1.4` + `pnpm atlas`），否则像素密度就和其它美术不一致了。

**对齐**：`--anchor-x left` 已经钉住鼻子（四帧的鼻子都在同一列，实测偏移 0）；
**垂直方向不能靠内容框居中**——尾巴摆出去时内容框跟着变，居中就等于让整条鱼上下晃（管线对生成版报的就是 `DRIFTING`）。
所以垂直方向按**头部区域**重新对齐（`.scratch/import-tuna-tail.py` 的最后一步），**而且是整像素平移**：
整像素平移不会重采样，身体才可能逐字节不变。
`--margin` 用 2 而不是默认的 8：新资产没有旧比例要保，而 8px 留白在 66 的网格上等于给 47px 的身体套 16px 边。

### 第 4 关的四个猎食者（座头鲸 / 海豚 / 大白鲨 / 章鱼）

第四关叫「猎食者温跃层」，它的想法是**水体本身从"有鱼的地方"变成"有猎食者的地方"**。所以这里有四个生物，
**行为和鱼、金枪鱼完全共用**（`CREATURES` 里都是 `stepFish`），区别只有体型——玩家要学的不是第四条移动规则，
而是"**那个东西有多大**"。这一条也是为什么它们是**四个 kind 而不是一个新机制**。

| | kind | radius | scale | 画出来宽 | 网格 | 成品 | 血 | 食谱门槛 |
|---|---|---|---|---|---|---|---|---|
| 座头鲸 | `whale` | 0.085 | 2.2 | 154px | 110 | 111×70 | 8 | 第 4 档 |
| 大白鲨 | `shark` | 0.07 | 2.4 | 138px | 99 | 98×61 | 6 | 第 4 档 |
| 章鱼 | `octopus` | 0.07 | 1.9 | 110px | 78 | 79×79 | 5 | 第 3 档 |
| 海豚 | `dolphin` | 0.055 | 2.0 | 91px | 65 | 66×50 | 3 | 第 3 档 |

**这四个值是一组，动一个就要动三个**：`hazards.radius` × `hazardArt.scale` 决定**画出来宽**，画出来宽 ÷ 1.4
决定**网格**，网格就是导入时传给 `import-sheet.py --drawn` 的数。改半径不改网格，这一只的像素密度就和别人不一样。
16 帧一共 110 KB。

**海豚是刻意的例外**：和鱼一样薄、第 3 档就能吞、`angry` 里是 `destroy` 而不是 `push`。
一关全是啃不动的东西，玩家就只剩躲了；它是这一关里"**大的也可以是食物**"的那一课，所以它第一个登场（`at: 390`）。

**四帧都是"只动尾巴"合成的，不是生成的**——`scripts/compose-swim-tail.py`，和上面金枪鱼同一条路线。
原始素材是四张 1024×1024 的 RGBA 成品图（`generated-images/big-swimmers/`），**自带透明通道**，所以没有走
`grant`/`key`。实测逐像素：**身体在任意两帧之间差 0 个像素**，尾巴差 160–457 个。四帧编码后共 110 KB。

**⚠️ 章鱼本来要走生成，最后没有走。** 它有八条腕、没有尾柄，`compose-swim-tail.py` 找不到那个"腰"——
它切在 x=844/1024，只转了最右边 180px。所以先试了生成四帧，测出来的数字是**不能上线**的：

| | 平均 \|ΔRGB\| | 差 32 级以上的像素 |
|---|---|---|
| 生成的四帧（章鱼） | **30.7–39.5 / 255** | **38–58%** |
| 合成的（金枪鱼 / 大白鲨，线上标准） | 1.0–2.1 / 255 | 1.3–2.2% |

生成的四帧是**四次完整重渲染**：连外套膜（唯一**不该动**的那部分）都差了 55–73%。这就是当初金枪鱼被否掉的
那个"煮"，而且更严重。所以章鱼也走合成路线，代价是**只有右边那条腕在动**（摆幅给到 `--amplitude 28` 才看得出来）。
`scripts/compose-swim-tail.py` 的 `--amplitude` 就是调这个的。

**两个脚本的接口本来接不上，这次修了。** `compose-swim-tail.py` 结尾打印的是
`python scripts/import-sheet.py <它的输出目录> --cols 4 --rows 1`，而 `import-sheet.py` 对参数做
`Image.open()`——照那行命令原样执行会在 Windows 上得到 `PermissionError: [Errno 13]`。
现在 `import-sheet.py` **接受目录**（一帧一个文件），把四帧拼成一条带 16px 间隔的 strip；间隔要大于 4px 是因为
`components()` 先做 4×4 分块再找连通域，靠得太近的两帧会粘成一个。
**而且目录输入走的是"共同画布"而不是逐帧内容框**——这是关键的一处：按各自内容框裁再按固定宽度缩放到网格，
尾巴摆动会改变内容框（实测四帧 983 / 982 / 974 / 958），于是缩放系数不同、**身体被放大缩小**，
第一次导入时身体帧间差了 1752 个像素。合成路线的全部承诺就是"身体不动"，导入器不能把它破坏掉。

**没做进这一轮的两件**：珊瑚（`coral`）和管虫（`tube`）**已经是障碍物种类**，但障碍物是 `paintObstacles`
用 Pixi `Graphics` 纯代码画的，没有任何贴图能力，而图鉴图标也走同一个入口。要让它们用图，得先给障碍物渲染器
加一层贴图+动画支持——那件事在这一节之后做完了，见下面"障碍物的贴图"。三张原图（珊瑚 1/2、管虫）收在
`generated-images/decor/`，其中珊瑚 2 还没用上。

**这四个的图鉴条目也补上了**（`src/codex.ts` 的 `ENEMY_PROSE`）：它们是这一关的设计本身，所以四条文案写的是
**体型各自让玩家付出什么**，而不是各自"做什么"——因为它们做的事情完全一样。

### 障碍物的贴图：珊瑚和管虫改用真图（`obstacles.art`）

障碍物原来的四种全是 `paintObstacles` 用 Pixi `Graphics` 画出来的（木箱是方框加木纹、珊瑚是圆加五条旋转的枝）。
现在**珊瑚和管虫改用图片**，木箱/封路木箱/渔网照旧用代码画——`obstacles.art` 是一张**稀疏表，一种一行**，
两版是二选一而不是叠加。

| | image | scale | 画出来宽 | 网格 | 成品 |
|---|---|---|---|---|---|
| 珊瑚 | `珊瑚` | 1.35 | 111px | 79 | 83×71 |
| 管虫 | `管虫` | 1.0 | 62px | 44 | 48×78 |

**画出来宽度还是那套算式**（`2 × obstacles.radius × 412 × scale`），所以它和 `hazards.radius` 一样：
**改 radius 或 scale 就要重跑导入**，否则这一种的像素密度和别人不一样。两张图一共 17 KB。

**动画是"绕底部微微地转"，不是几帧**。`swayDegrees` / `swaySeconds` 两个数值就是它的全部：
`art.coral.swayDegrees: 3` 加 `swaySeconds: 6`（珊瑚是硬骨架，摆得含蓄），管虫 6 度 / 3.2 秒（软管子，摆得明显）。
**为什么不做帧**：一张图绕底转，身体是同一份像素，构造上不可能变；而生成四帧实测平均差 30–40/255，
是线上合成版（1.5/255）的二十倍——那条路在上面章鱼那节已经被否过一次了。
每一株的相位用障碍物自己的 id 乘黄金角错开，否则第一关那种**一整排**管虫会像栅栏一样同时摆。

**锚点在图片的底部中心**（`anchor.set(0.5, 1)`）：障碍物所在的那个点保持不动，图片在它上面倾。
锚在中心的话，一株倾斜的珊瑚会把底座从自己身下甩出去。

**受损反馈一点没丢**：图片是精灵，暗化走 `sprite.tint`，而裂纹和命中白闪本来就是画在同一个 `Graphics` 里的
两道独立工序，所以**给障碍物上贴图不用重做任何一套伤害表现**。图还没加载出来时自动落回代码画的那一版
（和生物一样，"图"永远是升级，不是前提）。

**新增工具 `scripts/import-picture.py`**：`import-sheet.py` 是给会动的生物用的（找帧、按头对齐、多帧共用一个调色板），
把一张静图塞进去只会得到 `珊瑚-1.png` 这种"看起来还应该有第二张"的文件名。新脚本就是去掉对齐那一半的单帧入口：
裁到内容、按密度像素化、写 `src/assets/<名字>.png`。**它没有默认值**——`--drawn` 或 `--grid` 必须显式给，
因为 `import-sheet.py` 不给参数时读的是金枪鱼的数，那个坑不值得再挖一次。

### 修：图鉴里所有敌人的图标以前一直是"代码画的替身"

顺手发现的，而且**不是这次引入的**：从菜单直接打开图鉴，每张卡上的敌人都是 `drawFish` / `drawJelly` 那种
程序化形状——一条鲸鱼被画成一条通用的鱼。

两个原因叠在一起：

1. **贴图和动画都是"用到才加载"**。加载页对水域是对的（生物出现后一两帧就位，没人看得出来），
   但图鉴的卡片**只画一次**，画的那一刻没有就是一直没有。
2. 更要命的一个：图鉴每张卡都新建一个只有一只生物的一次性 field，而它们的 **id 全都是 1**。
   精灵池是按 id 缓存的，所以**整页卡共用一个精灵，只有最后画的那张拿得到**。以前看不出来，是因为
   图鉴里从来没有贴图可用，所有生物都走"代码画"那条路，而精灵池只在有图的时候才被用到。

两处都修了：进图鉴时自己也加载一次（`preloadAssets` + 新的 `warmAnimations`，加载完再 `refresh` 重画当前页而不是
回到第 1 页），以及**每张卡拿到一个自己的、水里永远不会用的负 id**（`Card.iconId`）。现在图鉴从菜单打开就是全套真图。

### 珊瑚：一种障碍物，七张脸（`obstacles.art.<kind>.variants`）

一关的礁床不该是同一丛珊瑚复制二十份。所以障碍物的贴图从"一张图"变成**一组**：

```json5
"coral": {
  "variants": [
    { "image": "珊瑚",      "scale": 1.35 },   // 111px，网格 79
    { "image": "珊瑚-团状", "scale": 1.41 },   // 116px，网格 83
    { "image": "珊瑚-桌状", "scale": 1.46 },   // 120px，网格 86  ← 最大
    { "image": "珊瑚-枝状", "scale": 1.07 },   //  88px，网格 63  ← 最小
    { "image": "珊瑚-扇形", "scale": 1.26 },   // 104px，网格 74
    { "image": "珊瑚-管状", "scale": 1.36 },   // 112px，网格 80
    { "image": "珊瑚-鹿角", "scale": 1.3 }     // 107px，网格 75
  ],
  "alpha": 1, "swayDegrees": 3, "swaySeconds": 6
}
```

**每个障碍物按自己的 id 稳定地挑一个**（`id % variants.length`）——不随机，所以一株珊瑚从生到死都是同一张脸，
重绘也不会让整片礁床重新洗牌；不记状态，所以多一个变体一分钱不花。id 是按生成顺序发的，所以一**排**珊瑚会依次
轮遍整套，而关卡真正的变化本来也主要来自它自己的间距。

**碰撞、血量、碎裂、缺口计算全部不变**——变体只换图。一丛珊瑚本来就该是"同一个东西的不同长相"，
而不是六种不同的障碍物（那要六套 `radius`/`health`/`ramVolume`，而它们的碰撞完全一样）。

**大小差写在每张自己的 `scale` 里**：88–120px，围着碰撞直径 82.4px 上下浮动——比圈小的看着"好过"，
比圈大的看着"占地方"。这七个值仍然遵守那条算式（`2 × radius × 412 × scale` = 画出来宽度，÷1.4 = 网格），
所以改任何一个都要按新宽度重跑 `import-picture.py`。

**`珊瑚-鹿角` 是第一条走完整条资产管线做出来的**（`asset_flow.py`，见 `.claude/skills/game-asset/SKILL.md`）：
Wikimedia 上一张鹿角珊瑚的照片 → `grant` 种透明 → flash 图生图出 3 张候选 → 按上面的算式像素化 → 挑一张 → 入库。
**它的 `scale` 是 1.3 而不是凑到密度 1.4 的那个值**：算出来 1.39，而库里六个珊瑚实测都在 1.32–1.34
（它们是 `- 2 × margin` 那条修正之前的产物，整体偏粗约 5%），所以这里跟邻居对齐、没有跟公式对齐。

**这一批最该记住的教训是构图，不是密度**：前 3 张候选在调色板（40 色封顶）、密度（1.39）、边缘频率
（67–72% vs 已入库 67–81%）上**全部达标**，却一眼就不对——因为库里的珊瑚**全是小场景**（珊瑚 + 礁石沙砾底座 + 一两株伴生物），
而候选是**一株孤立珊瑚**：实测底部 10% 的填充宽度只有 **30%**，邻居是 **65–88%**。修好的办法是给提示词加一段
`composition`，而不是动管线。

**四张新珊瑚是生成的**（`.scratch/big/corals.spec.json`，flash、1K，一次四张、共 56 秒），
风格统一靠的是**同一张参考图 + 同一段风格描述**，而四帧各自描述形状（低宽的桌状 / 高细的枝状 / 摊开的扇 / 一丛管状）。
底座都在图片底部，而精灵锚在底部中心，所以**一排珊瑚会连成一条连续的海床**——这是它摆在关卡里最像环境的地方。

### 电鳗和海胆：一张图各自解决一个老问题

这两个种类一直是 `drawEel` / `drawUrchin` 用代码画的，现在换成原图。

**电鳗**要"待机 + 放电"两个姿势，而**放电那张直接接在它现有的射击上**：它本来就会放电箭
（`enemyBullets.shooters.eel`，1.1 发/秒、射程 420m、`shape: "bolt"`），所以开火的那一瞬间切到带电弧的那张，
过 `hazardArt.eel.attackSeconds`（0.45 秒）回待机。**没有第二个机制**——玩家看到的"它电你了"就是它开火的样子。
0.45 秒是刻意的一半：射一发的间隔是 0.91 秒，电弧闪一下再熄；调到 0.9 就会让攻击图变成常态，待机那张白做。

两张图是**同一天、同一 `--drawn` 导入**的。这一点是量过才定的：待机图的内容框 971×806、放电图 925×609，
差得很多，但两张里**身体**占内容框的比例是 971/971 和 888/925——只差 4%，所以切换姿势时它不会忽大忽小。

**海胆**要"轻微的旋转"，而它本来就是一个放射状的刺球，转起来就是全部动画。所以 `hazardArt` 多了一个
**`spin`（每秒多少弧度）**，精灵绕自己的中心按 `spin × h.phase + h.seed` 转——用生物自己的时钟，
所以在一排里每个角度都不同（同一帧生成的两只不会像双胞胎）。**0.35 就是原来代码画那版的转速**
（`drawUrchin` 里的 `h.phase * 0.35`），所以换成图片之后手感不变；0 = 完全不转。

### 小鱼换成原图 + 游动循环（`fish`）

**游戏里最常见的生物**（六关一共刷 129 处）原来一直是 `drawFish` 用代码画的椭圆加三角尾，现在换成原图。
一条朝左的成品图 → `compose-swim-tail.py` 转尾巴 → 四帧，`hazardArt.fish` 指 `fish-swim`。
四帧身体逐像素相同，帧间只有 6–10 个像素不同（尾巴那一小块）。

**画出来 56px（网格 40），`scale 1.94`**。这个数是按旧版量的：代码画那版身体 3r 宽、尾巴伸到 2.2r，
全长约 53px。**鱼是全场的基准尺寸**——它变大或变小，别的生物的"大小"就读不出来了，所以这里刻意贴着旧版走。

**有一处只有贴图会丢的东西，单独补上了**：被诱饵控住的鱼会画一个呆滞的白眼。
那**不只是装饰**——被引诱的鱼既不追你（`stepFish`）、也不造成接触伤害（`contactFish`），
所以"哪些鱼现在被控住"就是**威胁状态本身**。代码画的那版是**把眼睛换成白点**，而图片自带眼睛，
所以那个白点现在是在精灵之后**重画上去的**，位置跟着 `facing`（精灵用的那个镜像），大小按图片宽度取比例。
第一版做得差不多大一倍，看着像车头灯而不是呆滞的眼睛——现在按旧版的比例（`r*0.16` 的点配 `r*0.2` 的眼）。

**尾巴的摆幅调大没有用**：试过 24 度，帧间差异还是 4–10 个像素——41 像素宽的网格上，
尾巴的运动已经量化到极限，再多转也落不到新的像素块上。所以留在默认的 15 度（和金枪鱼同一个数）。

**鱼不看玩家，看向自己游的方向**（`hazardArt.fish.facesPlayer: false`）。

"面朝玩家的气泡"对猎手是对的、对鱼是错的：屏幕上的鱼**绝大多数没有在追人**——`stepFish` 只在感知半径内才靠拢，
半径外只是自己 S 形漂。所以原来那些漂着的鱼会**集体转过头来盯着一个根本没注意到你的气泡**，
而**被诱饵控住的鱼**最刺眼：它正在往远离你的方向游，却回头看着你。实测（鱼和金枪鱼放在**同一个位置**，
玩家在它们右边）：

| | heading | facing | 读作 |
|---|---|---|---|
| 鱼 | -1（往左游） | **+1** | 面向游向（朝左），不理玩家 |
| 金枪鱼 | -1 | **-1** | 仍面向右边的玩家 |

**heading 写在动作发生的地方，不在画笔里重算**：`stepFish` 在它三个分支里各写一次（诱饵是"背离玩家"、
漂移是 `sign(sway)`、追猎是 `sign(steer)`），冲锋创建处写一次（冲锋期间 `stepFish` 不跑），
路径跟随写一次——**那处原来写的是 `h.seed` 的正负号，而全项目没有任何地方读它**，注释却写着
"The facing follows the tangent"，所以那段意图一直是失效的，现在由 `heading` 真正兑现。

`heading <= 0` 顺手覆盖了"还没决定"：没游过任何地方的生物保持原图朝左，而不是因为 heading 是 0 就镜像过去。
默认仍是"面向玩家"（猎手该面向猎物），只有鱼显式关掉。

### 修：spline 上的鱼群从**起点**出发，而且挨得更近

两件事，都是同一条曲线的读法。

**原来的做法**是把每条鱼**按序号摆在曲线的不同位置上**（`elapsed = seconds × i / n`）：整串一出现就已经铺满整条曲线，
所以中间那几条是**凭空出现在曲线中段、而且已经在动的**——没有任何东西交代它是怎么到那儿的。

**现在按时间错开**：整串一起在曲线的**起点**待命，每 `pathSpacingSeconds` 秒放走一条。
每条的 `elapsed` 从**负数**开始（= 还要等多久），而读曲线处把 `t` **两端都夹住**——这一夹不是装饰：
Catmull-Rom 是 `t` 的一个函数，负的 `t` 不是"起点"，是**往曲线前面外推出去的一个点**，
不加这一夹整队就会排到起点外面、谁也看不见它过来。

在起点等命**只有起点在屏幕外才成立**——本作的曲线全都从泳道边缘以外进场——因为**能被看见的队列就是一堆**。

**间距从"曲线的几分之一"改成"每条差几秒"**，`pathSpacingSeconds` 写在刷怪块上（`count` 现在决定这一串**有多长**，
不再决定有多密）。默认 0.5 秒：原来第 1 关的 weave 算下来是每条 0.75–1.25 秒，大约一个半身位的清水，
读起来是一条**散开的长队**而不是一群鱼。实测现在相邻两条中心相距约 0.13 泳道（≈54px，鱼本身 56px 长）——
再看截图，一群鱼首尾相接地游进来。

**时间而不是距离**：沿曲线量的间隔会在曲线变速时被拉伸和挤扁，而一群有节奏的鱼才是一群鱼。

### 小鱼有四个品种，**一个品种就是一群鱼**

`hazardArt.<kind>` 现在可以给一个种类**一组长相**（`variants`），而不是一张图：

```json5
"fish": {
  "facesPlayer": false,
  "variants": [
    { "move": "fish-swim",   "scale": 1.94 },   // 原来那条银色鱼
    { "move": "fish-swim-2", "scale": 1.94 },   // 细长的沙丁式
    { "move": "fish-swim-3", "scale": 1.94 },   // 圆钝的橄榄金
    { "move": "fish-swim-4", "scale": 1.94 }    // 竖条纹、黄橙鳍
  ],
  "alpha": 1
}
```

**行为完全一样**：四个都是 `stepFish`、都是 radius 0.035、掉一样的东西——品种只影响画出来是什么，
所以加品种**没有动过一行玩法代码**，`CREATURES` / `CONTACT_EFFECTS` / `KIND_TUNING` 一张表都没改。

**"一群"在代码里就是"一个刷怪块"**，所以品种**跟着块走**：`expandBlock` 把同一个 `variety` 发给它放置的每一条，
因为 `{ kind: 'fish', count: 6 }` 就是六条一起来的鱼，而一群鱼一半沙丁一半鲈是**两个群在假装一个**。
一条 spline 上的串同理，它也是一个块。

**品种号在鱼群之间轮转，不是在全部块之间**——这是量出来才定的：按全部块的序号时，第一关是 9 / 22 / 21，
`%4` 之后 1 / 2 / 1，两个鱼群之间隔着气泡和拾取物就会撞上同一个品种。现在 `blockVarieties()` 只数鱼块，
所以相邻两群**必然不同**（实测：0,1,2,3,4…）。随机刷怪（一次只来一条）没有群可以对齐，才每条随机。

**四条都朝左、同一个 `--drawn 56`**，所以换品种时体型不变；高度不同（14 / 21 / 21 / 22 像素）是它们本来的差别——
沙丁就是比鲈细长，这也是"符合鱼的特征"那一半：细长叉尾的沙丁、圆钝红鳍的拟鲤、竖条纹带刺背鳍的鲈。

四张新图同样是生成的（flash、1K，一次三张、40 秒），风格统一靠**同一张参考图 + 同一段风格描述**。

### 电鳗的电箭也会夺走操作（`hazards.eel.boltShockSeconds`）

电鳗的"短暂失控"最初**只有一条路**：把它吞下去，然后它在胃袋里每 2.4 秒电你一下。
结果是这条机制**对不惹它的人完全不存在**——而它恰恰应该是电鳗最响的那件事，也就是**它开火的那一刻**。

现在它的**电箭打中你也算电到**（这也是唯一的一条路，胃袋那条随库存一起删了）：`boltShockSeconds`
（默认 0.5 秒）之内左右反过来，气泡上套一圈**锯齿电光**（`shockColor` / `shockWidthRatio`）。
写成 0 就整条关掉，电鳗退回"普通的硬家伙"。

**实现上要改的一处**：`EnemyBulletField.update` 原来返回**命中数量**。数量能说"有东西打中你了"
（够扣一点血），但说不了"是什么打中你的"。现在它返回**命中的种类列表**——子弹本来就带着 `kind`
（它是从哪个发射者身上复制过来的），所以按种类结算不用新增字段，而"只有电鳗的子弹会电人"这件事
也因此写在明处：将来再加一个会放电的射手，得在这里**明说**要，而不是碰巧继承到。

### 修：所有带贴图的敌人都被随机转了一个角度（肚子朝上）

一个只有一行的 bug，但值得记下来，因为**它是被测试方式放过去的**。

海胆要"轻微自转"，所以精灵路径加了一行：

```js
sprite.rotation = (art.spin ?? 0) * h.phase + (h.seed ?? 0);   // ← 错的
```

没有 `spin` 的种类，`art.spin ?? 0` 是 0，但 **`+ h.seed` 还在**。而 `h.seed` 是 `Math.random() * 1000`——
于是**每一个有贴图的敌人**都被转了 0–1000 弧度：鱼、盲虾、金枪鱼、电鳗、四个猎食者、灯笼鱼、水母……
在关卡里翻的翻、倒的倒，而且看起来像"图画错了"，不像"算错了"。

**正确写法是把 seed 放进 spin 里面当相位偏移**，整个式子乘上 `spin`：

```js
const spin = art.spin ?? 0;
sprite.rotation = spin * (h.phase + (h.seed ?? 0));            // spin 为 0 时旋转恰好是 0
```

这样"没有自转的种类不旋转"就是**构造上成立**，而不是靠一个可能被删掉的守卫。实测（seed 设成 431.7，
即自然刷怪的随机量级）：鱼 / 盲虾 / 金枪鱼 / 电鳗 `rotation = 0`，海胆 `rotation` 在 151.287 → 151.392 之间推进
（0.35 弧度/秒 ✓，而 seed 只把它错相，所以两只海胆不同步）。

**为什么之前所有截图都没看出来**：`debugSpawnHazardOnPlayer` 走的是 `spawnForTest`，
而它传 `{ deterministic: true }` → **`seed = 0`**。所以每一条用那个钩子摆出来的敌人都恰好是正的，
包括我验证海胆自转、电鳗放电、小鱼换图的那几张。**那个钩子对"按实例随机的视觉"这一类 bug 是盲的**——
以后再用它看美术，要记得先把 `h.seed` 改成随机值再截图。

### 敌人贴图（`hazardArt`）+ 灯笼鱼的发光触角

按种类给图，**没给图的种类照旧用代码画**——一次换一种，不用一次全换：

```json5
"hazardArt": {
  "angler": {
    "move": "灯笼鱼-移动",     // 平时
    "charge": "灯笼鱼-冲锋",   // 冲锋时（h.charge 非空；没写就继续用平时那张）
    "scale": 1.5, "alpha": 1,
    "lure": { … }              // 触角发光，见下
  }
}
```

图片已导入：`src/assets/灯笼鱼-移动.png`、`src/assets/灯笼鱼-冲锋.png`（**现在各 80×80**，见"像素化"一节）。实测两张都能加载，画面里鱼是**贴图**而不是代码画的 ✓（这两张现在都在**图集** `atlas-1` 里：文件仍是这两个，只是要先 `pnpm atlas` 才会进游戏。）

**触角发光是代码加上去的**（图里没有）——这正是你问的那件事：加在图上意味着**每次调光都要重新导图**，而发光恰恰是这个敌人身上唯一**必须会动**的部分。参数都在 `lure` 里：

| 键 | 作用 |
|---|---|
| `stemAngle` / `stemFrom` / `stemLength` | 线的角度、起点、长度 —— **用它们把光点对到图里那根触角的尖端**（图里触角在左上方，现在默认 -28°） |
| `stemWidth` / `stemColour` | 线的粗细与颜色（设 0 就不画线） |
| `bulbRadius` / `bulbColour` | 光点本身 |
| `glowRadius` / `glowColour` / `glowAlpha` | 光晕（第一版给到 1.5 半径 / 0.5 不透明度，**糊住了半条鱼**，现在收到 0.5 / 0.22） |
| `pulsePerSecond` / `pulseMin` / `pulseMax` | 呼吸：每秒几次、最暗/最亮倍率 |

### 每个敌人自己的姿势 + 自己的冲锋窗口（修：灯笼鱼张嘴的时机）

**你报的 bug**：灯笼鱼在**蓄势**时就张开了嘴，真的扑出去时反而闭嘴——正好反了。原因不是画错了，是**一个共享分支**：

```ts
// 修之前，所有敌人共用这一句（它是为盲虾写的）：
state = windingUp ? (art.charge ?? art.move) : art.move;
```

"蓄力图属于前摇"对**盲虾**是对的（它前摇时蜷起来、扑出去时伸开），于是那次为盲虾做的修正**悄悄改掉了灯笼鱼的时间轴**。

**修法：姿势选择变成"每只生物一张函数表"**——和运动（`stepFish`…）、绘制（`drawJelly`…）、接触（`contactFish`…）同一套做法，
这是第四张。默认规则是"前摇用 charge 图"（大多数生物如此，盲虾照旧），灯笼鱼覆盖成**自己的一条规则**。
死亡和 BOSS 的挥螯**在同一个地方统一处理**，所以任何一只自己的规则都不可能忘记它们。

**灯笼鱼最终的样子：整个冲锋都用张嘴图**——蓄势（0.55s）张嘴、扑击（0.45s）保持张嘴、咬完闭嘴上。
**这一条是改了两次才对的**，两次都记在这里，因为两次的错法正好相反：

| 规则 | 蓄势时 | 扑击时 | 错在哪 |
|---|---|---|---|
| 共享分支（最初的 bug） | 张嘴 | 闭嘴 | **正好反了**：张嘴（那口咬）出现在前摇，扑出去时反而闭嘴 |
| 只属于扑击（上一次的修法） | 闭嘴 | 张嘴 | 反过来了但仍然不对：**咬出去之后才张嘴，那不是预警** |
| **整个冲锋（现在）** | **张嘴** | **张嘴** | —— 张开的嘴**既是预警也是那一口咬** |

这个决定现在是**纯函数**（`hazardArtPose`）并导出了，因为这次的 bug **编译器和仓库里所有探针都看不见**：
现在一条命令就能问出来（`scripts/probe-poses.mjs`，实测输出）：

```
creature   pictures                       winding up        lunging           after the charge
shrimp     move=盲虾     charge=盲虾-蓄力      盲虾-蓄力             盲虾                盲虾
angler     move=灯笼鱼-移动 charge=灯笼鱼-冲锋     灯笼鱼-冲锋            灯笼鱼-冲锋            灯笼鱼-移动
```

**顺着这条线又挖出一个同源的 bug**："这次冲锋的前摇有多长"这件事，**四个地方各答了一次**，而且答得不一样：
运动（`advance`）和画笔读 `charges.chargers`，灯笼鱼没有行 → 拿到**小鱼的 0.75**；
而 `main.ts` 里的**冲刺拖尾**专门为灯笼鱼开了个后门，读它自己的 **0.55**。
后果正好踩在拖尾自己写下的那条规矩上（"前摇时冒泡等于说'它已经走了'"）：**灯笼鱼还在原地蓄势，身后就已经拖出一串气泡，早 0.2 秒**。
同时它自己的 `travelSeconds`（0.45）**没有任何代码读**，每次咬完冷却还被回退值 2.2 覆盖掉（它写的是 3.2）。

**修法：`chargeWindow(kind)` 成为唯一答案**，四个消费者（运动 / 画出来的预警弧 / 拖尾 / 用哪张图）全部问它；
**生物自己那块配置优先于共享表**（`hazards.angler` 里本来就写着它自己的那三个数，这正是配置正在走的方向）。

**实测的时间变化**（`probe-poses.mjs` 顺便量出来）：

| | 修之前 | 现在 |
|---|---|---|
| 灯笼鱼蓄势（玩家的反应窗口） | 0.75s（小鱼的值） | **0.55s**（它自己写的） |
| 扑击时长 | 0.55s | **0.45s** |
| 咬完到下一次的冷却 | 2.2s（被回退值覆盖） | **3.2s** |

也就是说：**它的咬变快了，但变得没那么频繁**——这三个数都是你自己写在 `hazards.angler` 里的，之前只有其中一个生效了一半。
实测一次完整的咬：0.55s 时闭嘴变张嘴（扑出），1.0s 咬完闭嘴。

**两处我故意没动**（都属于"你说了再改"）：① 灯笼鱼**第一次**咬仍然是在你进入 300m 引诱范围的瞬间就开始蓄势
（`spawnAt` 给"没有 chargers 行"的生物的初始冷却就是 0）；要像其它冲锋者那样随机错开，说一声。
② **图鉴里灯笼鱼那张卡没写它会扑人**：那张卡是从 `charges.chargers` 推导威胁行的，而灯笼鱼在那张表里没有行——
卡片现在只说了"碰到会怎样"。可以用同一个 `chargeWindow` 推导出来，但那是文案，留给你定。

### 修复：小鱼冲锋结束后"隐身"

**原因不是隐身，是卡住**：小鱼冲锋撞到玩家后被**打跑**（`flee` ✓），但它**身上还留着 `charge`** ✗。而 `charge` 分支在最前面并且**提前 return** ✗，加上敌人一旦离场就不再被推进 ✗ —— 于是这条鱼**永远冻结在冲锋姿势**里，同时又以"离场"的身份被画成**很淡**的一层 ✓✓ = **看不见又不动**，正是你看到的样子。

**修复**：**被打跑时把 `charge` 丢掉** ✓，交还给"离场"那套运动——那才是设计好的样子（淡淡的、游走）。

**实测**（真实冲锋打到玩家）：

| 时刻 | 场上 | `charge` | 结果 |
|---|---|---|---|
| 冲锋中 | ✓ | yes | — |
| 冲锋被打跑后 | **✓ 仍在场上** | **null** ✓ | 不再冻结 |
| 1.2 秒后 | 离场 ✓ | null | **正常游走离开** ✓ |

### 爆炸环：`explosions`

炸弹鱼炸开时画的那圈**会扩大的环**，**不是粒子**——粒子是"被打中的反馈"，这是"刚才那一下有多大"的读数，所以它是一圈环而不是一蓬碎屑。

两个同心圆，**外圈描边、内圈填充**：每个都有自己的**起始/结束半径比例**（相对爆炸半径，按寿命线性插值）、**颜色**、**起始不透明度**和**线宽比例**，全在 `explosions` 段里。寿命 `seconds` 是**同一个数字**：`step` 用它老化、绘制用它算进度，所以只有一处可改。

### 击中粒子：火花（已验证）与"打跑一圈碎片"（**未验证**）

配置在 `particles`：

| 键 | 含义 |
|---|---|
| `hitCount` / `hitSpeed` / `hitLife` / `hitSize` | **命中火花**：数量、速度（米/秒）、寿命、大小 |
| `defeatCount` / `defeatSpeed` / `defeatLife` / `defeatSize` / `defeatColour` / `defeatJitter` | **打跑碎片**：一圈向外等速的碎片（`defeatJitter` 是角度抖动，0 = 完美圆） |
| `maxParticles` / `drag` / `descentSpeed` | 上限（超了顶掉最老的）、每秒衰减、额外下沉 |

**为什么打跑是"一圈"而不是"一蓬"**：它是**散开**的，不是"又被撞了一下"——随机方向的爆发读起来是后者。

**架构**：**模拟只发出事件，表现才画粒子**——`hit()` 把事件推进**这个 field 自己的队列**（`HazardField.takeHitEvents()`），主循环取走。因为伤害来自好几处（子弹、连锁技能），而 `hit()` 是它们**唯一的汇合点**；在每个来源各调一次粒子系统，就是几个要记得改的地方。

> 队列从模块级数组搬到了 field 上：它装的是**这个 field 的 id 和半径比例**，而图鉴会用一个现造的一次性 field 走同一个画笔——共享队列意味着游戏会取走一次翻页产生的事件。

**实测**：`before 0 → 命中后 6` ✓（正好是 `hitCount`）。

**如实说明**：**"打跑一圈碎片"我没有验证成功** ✗ —— 第二次采样反而**掉到 5**，说明那一圈没有产生。代码在 `fled` 和 `killed` 两条返回路径上都推了事件，但我探针走的那条路径没有触发它，**原因未查明**。下一轮第一件事：把 `hit()` 的四条返回路径逐条打出来，看打跑究竟走的是哪一条。

### 一局的输出：`RunEvent` 队列

上一节的原则（**模拟只发出事件，表现才画粒子**）现在覆盖到**一局要说的一切**，不止火花。

| 事件 | 谁在听 |
| --- | --- |

每帧衰减（`updateTransientOverlays`）和绘制。

`Game.applyRunEvents()` 是**全文件唯一**碰这些东西的地方，它在**每个 step 之后**立刻跑（不是每帧之后），

### 加载页：进关前先把图片下完

**问题**：图片一直是"用到才下载"，于是**关卡开头那几秒**——玩家看得最仔细的时候——敌人会**从代码画的形状变成贴图** ✗，读起来像故障。

**现在**：点开始 → **加载页**（整屏，标题 + 进度条 + 下载字节数/网速）→ 图片全部 `decode()` 完成 → 才真正进关。阶段实测：**`loading` → `intro` → `playing`** ✓。（**改成图集之前**这里量到的是"下载 17 张图全部 200"；现在下的是 **4 个文件**：2 页图集 + 2 张远景 JPEG，见"图集"一节。）

几个判断：

- **一次下完所有图**，不是每关一份：整套美术 **0.49 MB**（图集 0.22 MB + 远景 0.27 MB；改成图集前是 6.45 MB），**下一关（包括自动过关）就再也不出现加载页**了。按关下载只会在每两关之间多插一屏，换不来什么。
- **报告的单位是"文件"，而现在一个文件通常是一页图集**：`total` 是 **3**（1 页 + 2 张远景），不是 27 张图。页面上的兜底行因此写的是"**文件** N / M"——数字要和旁边的 MB 讲同一件事，一个跟字节数对不上的计数读起来像 bug。
- **等 `decode()` 而不是 `onload`**：`onload` 是"字节到了"，`decode()` 是"位图能画了"——这个区别正是当初那句 0 宽纹理的教训。
- **缺图不算失败**：某个名字找不到文件时**记一次警告、算作完成**——一张图没了只该让一个敌人失去贴图，不该让整关进不去。
- **加载期间是独立阶段**：不接输入、不推进敌人、不走进度计时——**图片到达的过程中，玩家身上不会发生任何事**。触屏也是：这一页在显示层列表的最前面，而指针流**在 `handlePointerDown` 里就被挡掉**了——早先的进度条画在水面**下面**，"挡住"只是看起来挡住了，手指仍然能把气泡拖走。
- **大小是服务器报的**：每个文件一个 `HEAD`，读 `Content-Length`（`src/assets.ts`），不是构建期写死的清单——手工换一张图之后，页面上的数字仍然是对的。这些请求**不 await**：报告的准确性不许拖慢它所报告的东西。
- **网速按窗口测量**：显示的是最近 `speedWindowSeconds` 秒的平均值，不是"从开始到现在的总平均"——否则一次慢启动会在恢复之后还挂着一分钟。

配置在 `loading`：整页背景色/不透明度、标题内容/字号/颜色、进度条轨道色/填充色/高度/最大宽度、数字行字号/颜色/行高、三段竖向间距（标题→条→百分比→数字）、网速测量窗口。

### 敌人尺寸怎么调（**这就是答案**）

**文件**：`config/mechanics.json5`
**参数**：`hazards.radius.<种类>` —— 数字是**半径占泳道宽度的比例**（不是米，这样窄手机上"占屏幕多少"一致）。

```json5
"hazards": {
  "radius": {
    "shrimp": 0.066,   // 盲虾：0.033 → 0.066（2 倍）
    "angler": 0.09,    // 灯笼鱼：0.045 → 0.09（2 倍）
    "fish": 0.035,
    ...
  }
}
```

**它同时决定碰撞、绘制和图鉴卡片**——一处来源，改完**刷新即可，不用重新构建**。表里现在有 **24 种**
（这 24 就是 `hazards.radius` 的键；六只 BOSS / 喷泉 不在这张表里，它们的尺寸由各自的条目管——
BOSS 的在 `hazards.bosses.<kind>.radiusRatio`）。

**还有第二个尺寸参数，别混淆**：

| 参数 | 位置 | 作用 |
|---|---|---|
| **`hazards.radius.<kind>`** | `config/mechanics.json5` | **真实体型**：碰撞、绘制半径、图鉴卡片一起变 |
| **`hazardArt.<kind>.scale`** | 同上 | **贴图相对它有多大**（图里留白多就调大）——只影响观感，不影响碰撞 |

有贴图的敌人，**屏幕上看到的 = `radius` × `scale`**。想让敌人"更大更能打中"，改 **radius**；只想让图看着更大，改 **scale**。

实测：`shrimp 0.066` ✓ `angler 0.09` ✓ `fish 0.035` ✓

- **为什么导进来的是"等尺寸帧"而不是每帧各自裁剪的图**——这一条是这次唯一需要解释的决定：绘制时按**图片宽度**统一缩放（`hazards.ts` 的 `unit = size / texture.width`），而水母四帧的宽度**本来就不一样**（77 / 69 / 118 / 72 px，伞盖的收缩与张开**就是**这个宽度差）。逐帧裁剪后直接导入，等于每帧除以自己的宽度——**动画会剩下触手在动、伞盖不动**。所以四帧是从对齐好的长条上**用同一扇窗口**裁的（四帧内容的并集，`(27,19,145,193)`），尺寸一致 → 一个 `scale` 管住全部四帧，**管线做过的对齐一像素没动**。

- **实测**：四张图和管线自己的 `sheet/frame-N.png` **逐像素逐字节一致**（`4/4`，含"写出去再读回来"这一遍）✓；`check-art-names` → **ALL RESOLVE** ✓；`pnpm build` 四张图都在产物里（12.7 / 13.7 / 13.8 / 20.4 KB）✓；`preloadAssets(allAssetNames())` 自动带上它们（加载页那一套不用改）✓。

### 修复：冲锋时闪白不消失

**闪白原本在 `advance` 的末尾递减**，而**冲锋分支和路径分支都会提前 return** ✗ —— 于是"被打中 + 正在冲锋"的敌人**闪白根本不走时钟**，一直白到冲锋结束。你看到的正是这个：行走状态正常，冲锋状态白一整段。

**闪白是身体的状态，就该跟身体的时钟走**，而不是跟"这一帧恰好在跑哪种行为"走。现在它递减在 `advance` 的**最开头**，在**任何 return 之前** ✓。

实测：命中后 `hitFlash = 0.07` ✓ → 强制进入冲锋（`charging: true` ✓）→ **闪白正常衰减到 0** ✓（改之前它会卡在 0.07 直到冲锋结束）。

### 通用机制：敌人会转头面对玩家

```json5
"hazardFront": "left",          // 全局默认：图片的左边是"正面"
"hazardArt": { "angler": { "front": "left", ... } }   // 某种画反了，就在这里覆盖
```

逻辑一句话：**正面没有朝着玩家时就水平镜像**。玩家的气泡在敌人右边 → 敌人转向；在左边 → 保持。角度约定按你说的暂定**左边为正面**（灯笼鱼的图本来就是头在左 ✓），某一种敌人以后画反了，**改一个词**，不用改代码。

**为什么 X 轴可以直接取负、Y 轴不行**：世界只翻转了 Y（+y 向上）；X 是普通坐标轴，所以负的 X 缩放**就是**镜像，不需要像 Y 那样再抵消一次。

图鉴里**不转头**（卡片显示画师画的样子 ✓），因为没有玩家可看——`playerX` 是可选参数，图鉴不传。

实测：气泡右侧的灯笼鱼**朝左对着气泡** ✓（这条是对的）；**左侧那条我没能确认**——它看起来仍是朝左（也就是背对气泡），但我这一轮的量测钩子返回了 null，没有拿到数字，所以**不能算验证过**。下一轮我用坐标数字确认（而不是再看一次截图），顺手把那个返回 null 的钩子查清楚。

敌人的闪白**只有一个机制**了：贴图精灵在被打中时挂上颜色矩阵滤镜，**整张图变白**（RGB 输出 1、保留 alpha）；**那层盖在物体上的白色椭圆已经删掉**。

理由就是你说的：**以后的敌人都会用图片 sprite**，而"图片上面盖一个白团"不是"图片变白" ✗ —— 遮罩本来只是"敌人还是图形时"的临时替身。

**保留的例外，说清楚**：**可破坏的障碍物**（木箱/珊瑚/岩壁/渔网）现在**仍然用白色椭圆**——它们还是画出来的形状，椭圆是它们唯一的闪白。等它们的图也进来，同样换成精灵滤镜，这一行就是起点。

实测：被打中的灯笼鱼，精灵上的**滤镜数 = 1** ✓（`hitFlash` 0.14 ✓）——即"贴图变白"这条路真的挂上了。

### 玩家气泡的旋转（`playerBubble.imageRotation`）

**你看到的"转反了"不是贴图的问题，是坐标系的问题**：世界是**上下翻转**画的（世界 +y 向上、屏幕 +y 向下），所以放进世界容器的贴图默认是**镜像**的——代码画的气泡上下对称，谁也看不出来；换成有高光的图，一眼就看出来是倒的。

代码现在**自动抵消**那个翻转（`worldYIsFlipped` 沿父链把 Y 缩放乘起来判断，而不是只看直接父节点——第一版就只看了一层，结果对一个明显翻转的精灵报了"没翻转"），所以：

- **`imageRotation: 0` = 你的图保持原样朝上**（如上图：高光在上，正确）；
- 图上如果有别的朝向需求，`imageRotation` 就是**贴图自身的角度**（度，顺时针为正），正值转、负值回。

`imageScale` 也会一起复原——我上一轮打补丁时**误把你调好的 1.5 覆盖回 1**，已经改回 **1.5** 了。

### 最远景改到**水后面**，水暂时全部隐藏

按你的判断改了图层：**图在水后面**（`WorldLayer.root` 的第一个孩子 → `backdrop → gradient → margins → world`）。要让这一点成立，图必须是**屏幕坐标**——因为水体渐变是一个屏幕空间的填充，世界坐标的精灵会被摄像机变换、从它下面滑出去。所以图现在按**像素**定尺寸，滚动也是 `scrolled × speedFactor × 像素每米` 换算一次。

另外加了一张**同样的图偏移一整个图高**：单张图盖不住窗口——绕回会把它的上边缘扫过整整一个图高，一个循环里总有一段时间窗口越过了它的下边缘。两张就永远盖满。

**第一关的水现在 `waterAlpha: 0`（完全隐藏）**，先让你单独看这张图。看够了把它改回去就行：

- `waterAlpha: 0.35` → 水是很淡的一层雾，图主导；
- `waterAlpha: 0.6` → 水明显，图是暗处的背景（上一版的样子）；
- `waterAlpha: 1` → 完全不透明，图看不见（最初的 bug 状态）。

### 第一关的水色改成"薄雾"（不再遮住背景）

`palette.waterAlpha`（新键，0..1，默认 1 = 和以前一样完全不透明）：水体渐变现在按这个不透明度绘制，**低于 1 时它是一层水色薄雾，而不是一块不透明色板**——最远景那张海底火山图就能透出来。第一关设 **0.62**，同时把这层暗红的 `tintStrength` 从 0.22 降到 **0.14**（"过渡颜色太明显"主要是它）。其它关没有手绘图，保持默认 1，观感不变。

**为什么这才是对的形状**：图是画在**水里**的，不是画在水后面——所以"水盖住图"不是图层顺序问题，而是水的**不透明度**问题。

### 视差滚动：四层背景微粒

`background.layers` 四行，**由远到近**（绘制顺序也是这个顺序，第一行在最底层）：每行一个 `speedFactor`（关卡自身卷动的倍数）、`count`、`sizeRatio`、`colour`、`alpha`。

| 层 | speedFactor | 数量 | 说明 |
|---|---|---|---|
| 最远 | 0.08 | 90 | 几乎不动、最小最暗 —— 远处的悬浮物 |
| 远 | 0.22 | 70 | |
| 中 | 0.5 | 46 | |
| 近 | 1.0 | 26 | 跟着世界走，最大最亮；也最容易被误认成敌人，所以最稀 |

**为什么是四层而不是一层**：原来只有一层海雪，单一速度看起来就是**一堵会飘的点墙**，摄像机从旁边滑过去。四层四种速度才是空间——眼睛读的是**层与层之间的速度差**，那才是距离——场景里其它东西都不用动，"这片水有多深"就已经说出来了。

速度是关卡的**倍数**，所以卷动更快的关卡四层一起更快，而**相对运动**（眼睛真正读的东西）不变；最近那层是 1.0，其它三层靠它定位。每层自成一个 `tileScreens` 屏高的纵向带，微粒按世界米摆一次，层的位置 = `scrolled × speedFactor`（**不是累加器**——所以传送、卡帧都不会把它抹开或卡住），超出可见带的按带高绕回，有限的粒子覆盖无限的上浮。

实测：`scrolled` 从 200m 走到 600m（即 400m），四层分别移动 **32 / 88 / 200 / 398 米**，正好是 `400 × speedFactor` ✓ 由远到近递增 ✓；粒子数量与外观全在配置里 ✓

顺带修了一个老问题：渐变的量程原来用的是**第一关的长度**，所以比第一关短的关卡永远到不了自己的浅水色——现在用关卡自己的 `scrollLength` ✓

**背景音乐按关卡合成**（`audio.music.tracks`，键是关卡 id）：这个项目没有任何二进制素材，所以一段音乐是一份**配方**而不是文件——调性 `rootHz`、琶音速度 `stepPerMinute`、低通 `cutoffHz`（低=闷在水下，高=明亮开阔）、和弦进行与琶音型。两个声部：一条持续 pad + 一条琶音。

音乐跟着**本局**走：菜单静音，进关起播，换关换曲，音量走设置里那根滑块（同一个主增益，没有第二个音量控制）。实测（真实点击解锁音频后进入第一关）：`playing: true`、`audio: true`、曲目 `rootHz 55 / 44 步每分 / 4 个和弦` ✓

### 修复：BOSS 的一切都挂在"玩家在哪"上（"第二关的 BOSS 又没有出现"）

这是上一个修复的另一半，而且更根本：BOSS 的**出现位置和悬停位置都相对于玩家**。

- 入场点原来是 `玩家.y + 可见深度 × 0.62`。只有玩家贴着摄像机时这才等于"从画面上方进来"。**第二关的通道很窄、还有撞不碎的封路木箱**——被挡住的玩家会被水流甩在摄像机下面，这时按玩家算出来的入场点就在画面**下方很远**，生成后立刻被清理掉，谁也没看见。
- 悬停高度也按玩家算，同样的问题：玩家掉在后面，BOSS 就悬在**他**头上，而不是在打斗发生的地方。

现在两处都以**摄像机/可见带**为准：

- **入场**从可见带顶部上方 42% 处进来（`camera.y + band × 0.42`），不再看玩家在哪；
- **悬停**现在完全按可见带巡逻：中心在可见高度的 70%（`patrolCenterRatio`），上下浮动 8%（`patrolVerticalAmplitudeRatio`），周期独立；位置再按 BOSS 自身的贴图半高夹紧，保证整只都在屏内。

一句话：**"存在但不在屏幕上"和"不存在"对玩家是同一件事**，而关卡只有打死它才结束——所以它永远必须在屏内。

实测（第二关，且每帧把玩家强行拖到摄像机下方 400m，模拟被卡住）：

| 窗口 | 可见深度 | BOSS 相对摄像机 | 在屏内？ |
|---|---|---|---|
| 412×915 | 802 m | −18 m | ✓ |
| 1280×720 | 289 m | +47 m | ✓ |
| **1600×420**（极扁） | **168 m** | +52 m | ✓ |

### 修复：冲锋拖尾画成了 BOSS（"金枪鱼和灯笼鱼的冲刺变成了水母"）

**症状**：敌人冲锋时身后那串气泡（`chargeTrail`，"rides behind every charge"）变成了**又高又窄的冠冕水母竖条**，
盖在玩家气泡上。第 1 关并没有水母。

**根因**：`src/chargeTrail.ts` 把那张 6 格气泡表**切成 6 块**，而它切片的原点是**图集页的左上角**，不是这张图自己：

```ts
// 错的：source 是整页，frame 却从 (0,0) 起算
const fw = Math.floor(sheet.width / cfg.columns);
new Texture({ source: sheet.source, frame: new Rectangle(col * fw, row * fh, fw, fh) });
```

`loadAssetTexture` 返回的是**页里的一个矩形**：`sheet.source` 是整页（现在 1308×3188），
`sheet.frame` 才是这张图在页里的位置。所以那 6 块是从**图集左上角**切的——切到的是**恰好打包在那里的东西**。

**为什么一直没暴露，这一点比 bug 本身值得记**：打包器**碰巧**把这张图放在了 `(2,2)`，也就是全页第一个槽位。
于是"图集左上角"和"这张图的左上角"是同一个地方，错误只有 2 像素，谁也看不出来。
这一轮加进 80 帧 BOSS 图之后，它被挪到 `(336,656)`，那 6 块切到了排在我新图首的 BOSS——**症状才会以"水母"的形式出现**。

**修法**：按 `sheet.frame` 偏移，而不是从零起算：

```ts
const frame = sheet.frame;
const fw = Math.floor(frame.width / cfg.columns);
new Texture({ source: sheet.source, frame: new Rectangle(frame.x + col * fw, frame.y + row * fh, fw, fh) });
```

**验证是确定性的，不靠跑游戏碰运气**：把同一张图按新旧两种算法各切一遍，逐块问它落没落在这张图的边框里
（`node .scratch/asset-pipeline/cut-page.js`）：

| | 6 块的位置与尺寸 | |
|---|---|---|
| 旧 | `0,0` `47,0` … `235,0`，各 **47×284** | 全部**在图框之外**——在切图集 |
| 新 | `336,656` `383,656` … `571,656`，各 47×284 | 全部**在图内** |

`47×284` 就是 1:6 的竖条，和截图里那条水母的宽高比一致——形状这一半也对上了。

**另外两处同区域的小加固**（都不是这个 bug 的原因，但都是真的，一起留下了）：
`ART_SPRITES` 是按 `h.id` 键的**模块级**贴图池，而 `HazardField.nextId` 每个 field 都从 1 开始数，
游戏自己的 field、图鉴每张卡新建的临时 field 都会发出同一批 id——`NEXT_HAZARD_ID` 因此提到模块级，
让 id 在跨 field 意义上唯一；以及纹理没解析出来时把 sprite **藏起来**，而不是留着上一次贴的图和位置。

### 修复：宽窗口下 BOSS 悬在画面外（"第一关的 BOSS 没有出现"）

BOSS 的悬停高度原来是一个**绝对值 330m**。手机上可见深度约 802m，330 稳稳在屏内——所以我按手机尺寸做的每一次验证都通过了；但**窗口越宽越扁，可见深度越小**：

| 窗口 | 可见深度 | BOSS 悬停高度 | 屏幕上半高 | 在屏内？ |
|---|---|---|---|---|
| 412×915 | 802 m | 330 m | 401 m | ✓ |
| **1280×720** | **289 m** | 285 m | **144 m** | **✗ 跑到屏幕上方** |
| 900×600 | 241 m | 260 m | 120 m | ✗ |

BOSS 悬在画面外，玩家永远看不到它；而这一关只有打死它才结束——所以表现就是"BOSS 没有出现"。

现在高度由**可见带**推出来：中心 = 可见深度 × `patrolCenterRatio`（0.7），上下浮动 = 可见深度 × `patrolVerticalAmplitudeRatio`（0.08），周期是独立的 `verticalPatrolPeriodSeconds`；实际位置再按 BOSS 自身的贴图半高夹紧，保证整只都在屏内。纵向不再读取玩家位置。

实测（同一套探针，三个窗口重跑）：**802m → 286m**、**289m → 112m**、**241m → 95m**，三个都 `onScreen: true` ✓

### 一局跨六关：进度图 + 分数继承 + 自动进入下一关

击败一关的 BOSS 之后，这一局**不会**停在结算卡上：如果还有下一关，玩家带着**分数**直接走进下一关；只有**最后一关**才是这一局的终点（结算卡只在那里出现）。

- **分数继承**：`startRun(carryScore)` —— 死亡重来是 0，走关是带着走。分数是一局的总账，停在 0 就永远说不出"这一趟下潜走得怎么样"。（飘字仍然会清空：上一关留下的 `+25` 浮在这一关上是没有事件支撑的数字。）
- **自动进入下一关**：BOSS 死亡的收尾动画播完后交接（不是立刻切，否则胜利横幅还挂在屏幕上人已经在新关卡里了）。切关走的是菜单用的同一个 `selectLevel`，所以"通关走过去"和"从菜单点进去"是同一件事。
- **右上角的总进度图已经删掉**：原来是 `hud.progressChart`，屏幕右上角一行六颗小圆点，通一关点亮一颗，当前那关套一个金圈，下面一行"总进度 N/6"，画的是**本局**清关数而不是存档里的解锁列表。配置里的 `hud.progressChart` 一段、`HudState.progress`、以及背景层的 `progressGauge` / `progressLabel` / `redrawProgress` 一起删掉了。

实测：第 1 关 0/6、分数 0 → 打死烟囱蟹王 → **自动进入沉船幽谷**、分数 **1000（继承）**、横幅写着「第 2 关 · 沉船幽谷 · 分数继承 1000」 ✓

### 主菜单的关卡选择会换行

关卡药丸**按行排列**：一行的数量由 `menu.levelMinWidthRatio`（默认 0.3 = 一行 3 颗）决定，放不下就换到下一行、每行居中，说明行始终贴**最后一行**下面。

这是修一个真实的 bug：以前是**一行均分**，三关时看着正常，六关时每颗药丸只有自己名字三分之一宽，**六个名字叠在一起**。关卡行本身是一次**选择**，读不出名字的按钮就不是选择。

### 作弊：无限血量

设置面板里新增了 **作弊 / CHEATS** 一节，目前只有一项：**无限血量**（默认关）。开着的时候：

- 任何**命中**（碰撞、敌人子弹、爆炸）都**完全不发生**——不是"掉血之后补回来"，而是连受击音效、闪白、统计都不产生（`takeHit` 直接返回）。所以无敌的气泡和"从来没被碰到过"在任何可观察的层面都一样。
- **持续掉血**（垃圾袋的吸、海胆的放血）也走同一条路，所以也会被挡掉。
  （"过饱爆炸"曾是从内部来的第三条死法，随胃袋一起删了——作弊只需要挡住从外面来的那两种。）

它是**会话内**的开关、不写 `localStorage`：和音量同一个待遇，而且"重载后仍然开着"的作弊正是有人会忘记关掉的那种。实测：默认关 ✓；打开后把一条鱼按在气泡上 4 秒 → **存活**、`hits` 统计 **0**、关卡没有结束 ✓；再关掉 → 同一条鱼立刻造成伤害 ✓（开关真的是开关）。

**导电连锁**（第三关，已实现）：气泡是一个电容。被 `zapper`（电击水母）的放电环扫到加一大截电荷，靠近它会慢慢加，
不在电场里会泄露；**电荷过阈值后靠近任何一只水母就会引爆连锁**，放电在它们之间按距离跳（最多 12 只、每只 4 点伤害）。
带电时气泡外面套一圈电（线宽 = 电荷，到阈值开始闪），放电是一圈扩散光环。于是同一个机制同时是**危险**（带电时你会
引爆整片水母林）、**武器**（主动带电去炸敌群）、**路线解谜**（把电导向封路的触须）。实测：4 只围成一簇 → 环触发、
连锁把 4 只全部打跑。

`zapper` 是全场唯一"**越打越危险**"的敌人：碰到或**被打中**都会放一圈电，而放电环的半径就是判定半径。

## 附：从规则节里搬出来的实测记录

这些段落原本散在 README 的规则节里。它们证明某条规则**被验证过**，但那不是规则的一部分——
README 只回答"现在是什么规则"，验证留在这里。每一段都标着它原来在哪一节。
**（原在「气泡成长阶段的外观」）**

实测三个阶段画出半径 17.5 / 32.3 / 42.0 px，轮廓色 `#d8fbff` / `#ffcf6b` / `#ff8fbe`。

**（原在「弹幕：逼你不断移动」）**

实测（412×915，玩家体积 1.8 所以吃不了鱼）：站着不动 → **被撞中 1 次**；蓄势期间横向挪开四分之一个泳道 → **0 次**。同一条鱼两次冲锋的间隔 **3.49 秒**，正好是 `cooldownSeconds + telegraphSeconds + travelSeconds`（2.2+0.75+0.55 = 3.5）。冲锋路径距"起点—终点"直线最远 **33 米**（227 米冲锋的 15%，即 `bowRatio` 的一半，与二次贝塞尔的性质一致）。水母的冲锋实测：起点与它**自己身体的当前位置重合**（相差 2 米，就是起跳那一帧的漂移），蓄势期间位移 **0 米**——它不再"先走到某个位置再跳"，而是**原地起跳**，弧线完全由 `bowRatio` 提供（实测偏离弦 15% ≈ 0.85 的一半）。

**（原在「弹幕：逼你不断移动」）**

实测：静止不动站 5 秒 → 电鳗打中 **4 次**、体积正好掉 **0.8**（4 × `volume.hitCost` 0.2）；中间放一个木箱 → 只中 **1 发**（掩体是"挡住大部分"，不是"绝对安全"）；**一直横向走** → **0 次**。三种生物的射速实测 0.76 / 1.3 / 0.6 组每秒，和配置的 0.7 / 1.1 / 0.45 一致（多出来的是测试生成的第一次立即开火）。

**（原在「吸附（长按产生吸力）」）**

**（原在「路径点（spline）：一串敌人沿同一条曲线游过屏幕」）**

实测（第一关 `weave`，6 条鱼）：**从右侧 1.21 泳道宽处进场** ✓、横向走到 **−0.05** 并从左边出去 ✓、过程中在 **280m** 的高度范围内上下摆动 ✓ —— 就是"从屏幕右侧出现一串鱼依次上下游动、最后从左侧游出"。
